## 1. 照做就行：从零到跑出 Hello, World

这一章是纯操作。跟着做完，你会得到一个能编译、能断点调试、中文不乱码的 C 语言环境。

**这一章预计要花 30～60 分钟。中途不要跳步，尤其是第 3 步（加 PATH）和第 7 步（打开文件夹）。**

### 1.1 开始前，先确认三件事

**第一件：你的电脑是 Windows，而且是 64 位。**

怎么看：按键盘上的 **Win 键**（在 Ctrl 和 Alt 中间，上面有一个田字格窗口图标），然后直接打字输入 `关于`，在搜索结果里点 **"关于你的电脑"**。

在弹出的页面里找这两行：

```text
Windows 规格
版本            Windows 11 家庭中文版
系统类型        64 位操作系统, 基于 x64 的处理器
```

- 看到 **64 位操作系统** → 可以继续。
- 看到 32 位（很少见） → 你也能用，只是下载的时候要选文件名里带 `i686` 的包，本文按 64 位写。
- 完全找不到这个页面 → 在桌面上找到"此电脑"（或按 **Win + E**），在它上面**右键** → **属性**，也能看到同样的信息。

**第二件：你自己有一台能装软件的电脑，能用管理员权限。** 装 VS Code 的时候，Windows 可能会弹一个蓝底窗口问"是否允许此应用对你的设备进行更改"，点 **"是"** 就行。本文要改的 PATH 是"用户变量"，其实不需要管理员权限，所以不会频繁弹窗。

**第三件：联网，并且留出大约 1 GB 硬盘空间。**

> 术语不认识没关系（比如"右键""PATH""管理员权限"）。第 3 章专门补这些东西，遇到不懂的回来查即可。

### 1.2 你只需要会这 5 个鼠标和键盘动作

如果你已经会用电脑，这一段可以跳过。以下五个动作，在本文里会反复出现。

**动作一：单击、双击、右键。**

- **单击**（按一下鼠标左键）：选中某个东西。
- **双击**（快速按两下左键）：打开某个东西。
- **右键**（按一下鼠标右键）：弹出一个菜单，里面是"能对这个东西做的事"。**本文里 90% 的操作起点都是右键**。弹出菜单后不想选了，按键盘左上角的 **Esc** 关掉它。

**动作二：复制和粘贴。**

- 复制：选中文字或文件后，按 **Ctrl + C**（Ctrl 在键盘左下角，先按住 Ctrl 不放，再按 C）。
- 粘贴：在目标位置按 **Ctrl + V**。

**动作三：在"地址栏"里输入路径并回车。**

打开任意一个文件夹窗口，最上面有一条很长的输入框，那就是**地址栏**（它左边通常有一个小文件夹图标）。鼠标点进地址栏，用 **Ctrl + V** 把别人给的路径粘进去，按 **回车**，就直接跳到那个文件夹了。这是全文最省事的技巧。

**动作四：解压压缩包。**

你下载到的东西常常是一个"压缩包"（图标上带拉链，文件名以 `.zip` 或 `.7z` 结尾）。它相当于一个箱子，要先"解压"才能拿到里面的文件夹。

- **推荐做法**：先花三分钟照[第 3.6 节](#36-装一个顺手的解压软件bandizip)装好 **Bandizip**，之后在任何压缩包上**右键 → "解压到 <压缩包名>\\"**，一步到位，`.zip` 和 `.7z` 都认。
- **不装也行**：`.zip` 可以用 Windows 自带的 **右键 → "全部解压缩…" → 点"提取"**；但自带功能打不开 `.7z`。

**动作五：按组合键。**

看到 "**Ctrl + Shift + B**" 这种写法，意思是：**按住前两个键不放，再按最后那个键，然后三个一起松开**。最常用的两个组合键先记住：

- **Win 键**：打开开始菜单（要用它搜索软件和设置）。
- **Ctrl + `**（反引号，在键盘左上角 Esc 下面、数字 1 左边）：在 VS Code 里打开/关闭底部终端。

> 还有一个"通用救命键"：**Ctrl + Z** 是撤销。改错了先按它。

### 1.3 第 1 步：下载 MinGW-w64（用 WinLibs）

1. 打开浏览器（Windows 自带的 **Microsoft Edge** 就行），在**最上面的地址栏**输入下面这行，按回车：

```text
winlibs.com
```

2. 页面往下滚，找到 **Download** 这一块。你会看到一排文件名很长的链接，形如：

```text
winlibs-x86_64-posix-seh-gcc-15.2.0-mingw-w64ucrt-13.0.0-r1.zip
```

**你要点的就是这种：名字里有 `x86_64`、有 `ucrt`、结尾是 `.zip`。** 一般选排在最新（GCC 版本号最大）的那一行。

3. 不知道怎么读这个文件名？先记住这条：`x86_64` = 64 位，`ucrt` = 新版运行时，`.zip` = Windows 能直接解压。逐段解释在[第 4 章](#4-mingw-w64-是什么编译器版本和安装方式)。

4. 点下去就开始下载了。**如果浏览器提示"此文件可能会损害你的设备"，选"保留"**；这种包经常被误报，只要来源是 winlibs.com 就是正常的。

5. 下载完成后，在 Edge 里按 **Ctrl + J**，会打开"下载"列表。找到刚下载的那个文件，点它右边的 **"在文件夹中显示"**（或者直接记住：下载的文件一般在 `C:\Users\你的用户名\Downloads` 这个文件夹里）。

**你应该看到：** 一个文件名很长的 `.zip` 文件，体积大约一两百 MB。

> 下错了也不怕：只要不是 `i686`（32 位）的包，一般都能用；`.7z` 的包装了 Bandizip 之后也一样能解（[第 3.6 节](#36-装一个顺手的解压软件bandizip)）。名字里带 `mingw-w64` 才是现在活跃的那个项目，不要下成老的 `mingw`，详见[第 4 章](#4-mingw-w64-是什么编译器版本和安装方式)。

### 1.4 第 2 步：解压，并且把它放到 C:\mingw64

这一步的目标只有一个：**让 `C:\mingw64\bin\gcc.exe` 这个文件真实存在。**

1. 在下载文件夹里，**右键**你刚下载的压缩包：

   - 装了 Bandizip → 选 **"解压到 "<压缩包名>\\""**（会新建一个同名文件夹，最干净）；
   - 没装 → 选 Windows 自带的 **"全部解压缩…"**，再点"提取"。
2. 弹出的窗口里有一个"提取到"的路径框。保持默认（通常就是同一个文件夹里再建一个同名文件夹）也行，直接点 **"提取"**。
3. 解压完成后，会多出一个文件夹。名字通常是 `mingw64` 或者和压缩包同名。**双击进去，确认里面有 `bin`、`include`、`lib` 这几个文件夹。**

```text
winlibs-x86_64-posix-seh-gcc-15.2.0-mingw-w64ucrt-13.0.0-r1\
└── mingw64\
    ├── bin\        ← 这里面有 gcc.exe、g++.exe、gdb.exe
    ├── include\
    └── lib\
```

4. 接下来把 `mingw64` 这个文件夹搬到 C 盘根目录：

   - 在 `mingw64` 文件夹上**右键 → 剪切**（或选中后按 **Ctrl + X**）。
   - 打开"此电脑"（按 **Win + E**）→ 双击 **"本地磁盘 (C:)"**。
   - 在空白处**右键 → 粘贴**（或按 **Ctrl + V**）。

5. **改名检查**：最后必须是 `C:\mingw64`，里面直接就是 `bin`、`include`、`lib`。

```text
C:\
└── mingw64\        ← 正确的最终位置
    ├── bin\
    │   ├── gcc.exe
    │   ├── g++.exe
    │   ├── gdb.exe
    │   └── mingw32-make.exe
    ├── include\
    └── lib\
```

**两个新手最容易犯的错：**

- **错法一：多层套娃。** 变成了 `C:\mingw64\mingw64\bin\...`。多半是因为你把整个解压出来的文件夹又拖进了一个自己新建的 `mingw64` 里。解决：进到里层，把真正的那个 `mingw64`（或它里面的 `bin`、`include`、`lib`）移到 `C:\` 下，确保路径是 `C:\mingw64\bin\gcc.exe`。
- **错法二：放在桌面。** 路径变成 `C:\Users\你的名字\Desktop\mingw64\...`。如果你的 Windows 用户名是中文，整条路径里就带了中文，某些工具会莫名其妙报错。**请务必放在 `C:\mingw64`。**

6. 验证一下：在地址栏粘贴下面这行再回车，能不能看到 `gcc.exe`？

```text
C:\mingw64\bin
```

**你应该看到：** 一长串 `.exe` 文件，其中有 `gcc`、`g++`、`gdb`、`mingw32-make`。如果这些名字后面看不到 `.exe`，说明系统隐藏了扩展名，不影响使用（想让它们显示出来，见[第 3 章](#3-电脑基础补课文件文件夹路径终端)）。

> **安装过想卸载？** 直接把 `C:\mingw64` 文件夹删掉，再回第 3 步把 PATH 里那一行删掉即可，不写注册表、不留垃圾。

### 1.5 第 3 步：把 `C:\mingw64\bin` 加进 PATH

**为什么：** 你在终端里敲 `gcc`，Windows 不知道去哪找这个程序。PATH 就是 Windows 的"通讯录"，你把它登记进去，Windows 才知道 `gcc.exe` 住在哪。详见[第 5 章](#5-path-环境变量windows-的通讯录)。

**逐步操作（Windows 11 和 Windows 10 通用）：**

1. 按 **Win 键**，直接打字输入 `环境变量`。搜索结果里点 **"编辑系统环境变量"**。
   - 如果搜索不到：打开"控制面板"（Win 键 → 输入 `控制面板`）→ **系统和安全 → 系统 → 高级系统设置**。
2. 弹出的窗口叫 **"系统属性"**。点右下角的按钮 **"环境变量(N)…"**。
3. 新窗口分上下两半：

```text
┌─ 环境变量 ───────────────────────────────────────────┐
│  ← 上半部分叫"用户变量"，改这里就够了，不需要管理员  │
│  变量            值                                  │
│  ...                                                 │
│  Path            C:\Users\你\AppData\...\bin         │  ← 选中这一行
│  TEMP            C:\Users\你\AppData\Local\Temp      │
│                                                      │
│           [新建(N)] [编辑(E)] [删除(D)]              │  ← 点"编辑"
│                                                      │
│  ← 下半部分叫"系统变量"，本文不动它                  │
└──────────────────────────────────────────────────────┘
```

4. 在上半部分的列表里找到 **`Path`**，**单击选中它**，然后点 **"编辑(E)"**。
5. 又弹出一个窗口，里面是一行一行的路径（**这是全文最危险的一个窗口，请看下面的警告**）。点右边的 **"新建(N)"**，列表里会出现一个空的输入行，把下面这行粘进去：

```text
C:\mingw64\bin
```

6. 点 **"确定"**，一路点 **"确定"** 关掉所有窗口（一共要点三次左右）。

> **警告：不要点"删除"！** 这个列表里原有的每一行都是别的软件登记过的，删掉会导致别的软件坏掉。你只做"新建"这一个动作。
>
> **还要注意：** 粘进去的必须是 `C:\mingw64\bin`（目录），**不是** `C:\mingw64\bin\gcc.exe`（文件），也不要自己加引号或分号。

**加完 PATH 之后，如果终端（黑色或蓝色那个命令窗口）本来就开着，必须关掉重开。** 这一点在第 5 章解释，现在先照做。

### 1.6 第 4 步：新开一个终端，验证编译器装好了

**怎么打开终端**（任选一种）：

- 按 **Win + X**（先按住 Win，再按 X），在弹出的菜单里点 **"终端"** 或 **"Windows PowerShell"**；
- 或者按 **Win + R**，输入 `cmd`，回车（这样打开的是"命令提示符"，命令略有不同，下面会标出来）。

打开后是一个黑色或深色的窗口，光标在闪，等你去打字。**一条一条**输入下面这些命令（每行输完按回车）：

```powershell
gcc --version
g++ --version
gdb --version
where.exe gcc
```

- 前三条应该各自打印出版本信息，例如：

```text
gcc (MinGW-W64 x86_64-ucrt-posix-seh, built by Brecht Sanders, r1) 15.2.0
Copyright (C) 2025 Free Software Foundation, Inc.
...
```

（版本号和署名会和你下载到的版本一致。**只要看到类似这样的版本信息，就说明成功了。**）

- 在 **命令提示符（cmd）** 里，第 4 条要把 `where.exe gcc` 写成 `where gcc`。

- 最后一条应该打印出你安装的位置：

```text
C:\mingw64\bin\gcc.exe
```

**如果报错**，你会看到类似这两种之一：

```text
# PowerShell
gcc : 无法将“gcc”项识别为 cmdlet、函数、脚本文件或可运行程序的名称。
```

```text
# 命令提示符
'gcc' 不是内部或外部命令，也不是可运行的程序或批处理文件。
```

出现这个，**99% 是下面两种情况**：

1. 终端没有重开 → 关掉窗口，重新开一个，再试。
2. PATH 没加对 → 回到第 3 步检查：列表里应该有一行干净利落的 `C:\mingw64\bin`。

还有更细的排查在[第 11 章](#11-报错排查手册按现象找答案)。

**顺手用命令行跑一个程序**（可选，但强烈建议做一次，它能证明"工具链本身没问题"）：

在终端里一条条输入：

```powershell
mkdir C:\code\hello
cd C:\code\hello
notepad hello.c
```

第三条会打开记事本。把下面内容粘进去，然后关闭记事本窗口，在"是否保存"里选 **保存**：

```c
#include <stdio.h>

int main(void) {
    printf("Hello, C!\n");
    return 0;
}
```

回到终端，继续输入：

```powershell
gcc -std=c17 -Wall -Wextra -g -o hello.exe hello.c
.\hello.exe
```

**你应该看到：** 屏幕打印出 `Hello, C!`。

> `.\hello.exe` 前面那个 `.\` 的意思是"当前文件夹"，PowerShell 里运行当前目录下的程序必须这么写。在命令提示符（cmd）里可以直接写 `hello.exe`。

到这里，**编译器和调试器已经就位**。接下来装编辑器，把它们用起来。

### 1.7 第 5 步：安装 VS Code

1. 在浏览器地址栏输入 `code.visualstudio.com` 回车。
2. 点页面上那个大按钮（通常写着 **Download for Windows**）。下载到的文件形如 `VSCodeUserSetup-x64-1.xx.exe`。
3. 双击安装包。安装向导里**有两个勾建议打上**（英文版界面写的是括号里的内容）：

   - **"添加到 PATH"**（Add to PATH）；
   - **"将'通过 Code 打开'操作添加到 Windows 资源管理器目录上下文菜单"**（Add "Open with Code" action to Windows Explorer directory context menu）——勾上它，以后在文件夹上右键就能直接用 VS Code 打开。

   其他全部默认，一路"下一步"→"安装"→"完成"。
4. 安装完如果自动打开了 VS Code，会显示一个欢迎页。**先别急着乱点**，跟着下一步装扩展。

> 如果 Windows 弹出 SmartScreen 蓝屏提示"Windows 已保护你的电脑"，点"更多信息"→"仍要运行"（前提是你从官网下载的）。

### 1.8 第 6 步：装 C/C++ 扩展

VS Code 本体只是一个编辑器，**它自己不会编译 C**。让它认识 C 的是"扩展"。

1. 在 VS Code 里按 **Ctrl + Shift + X**，左侧会出现"扩展"面板。
2. 在搜索框里输入 `C/C++`。
3. 找到 **发布者是 Microsoft、名字就叫 "C/C++"** 的那一个（它的 ID 是 `ms-vscode.cpptools`），点 **Install（安装）**，等几秒。
4. 安装完成后，左侧列表里会出现它。

**注意别装错**：搜索 "C" 会出来一堆名字相似的扩展（`C/C++ Compile Run`、`C++ Intellisense`、`Code Runner`……）。它们不是本文要的，暂时都可以不装。

可选的：

- **中文界面**：搜 `Chinese (Simplified)`，发布者是 Microsoft，安装后重启 VS Code。
- **Code Runner**：搜 `Code Runner`。它能"一键运行"，但会把编译命令藏起来，**新手阶段先别装**，理由见[第 7 章](#7-vs-code-三个配置文件逐字段详解)。

### 1.9 第 7 步：建工程文件夹，写第一个程序

**先建文件夹（用鼠标就行）：**

1. 按 **Win + E** 打开文件资源管理器，双击 **"本地磁盘 (C:)"**。
2. 在空白处**右键 → 新建 → 文件夹**，输入名字 `code`，回车。
3. 双击进入 `code`，再用同样方法建一个 `c-course`。

现在你有了 `C:\code\c-course`。

**再用 VS Code 打开这个文件夹：**

1. 在 VS Code 里点菜单 **文件 → 打开文件夹…**（File → Open Folder…）。
2. 在弹窗的地址栏里输入 `C:\code\c-course` 回车，然后点 **"选择文件夹"**。
3. 如果弹出"是否信任此文件夹中文件的作者"，点 **"是，我信任此作者"**（这是你刚建的文件夹，放心）。

**新手最容易犯的错在这里：必须是"打开文件夹"，不能是"打开单个文件"。** 如果你只是把 `hello.c` 拖进 VS Code，那是在"打开文件"，`.vscode` 里的配置不会被读取，后面配的东西统统不生效。怎么确认？看左侧边栏的顶部，应该显示 **C-COURSE** 这个名字。

**新建代码文件：**

1. 在左侧"资源管理器"面板顶部，把鼠标移到 `C-COURSE` 那一行上，会出现几个小图标，点 **"新建文件"**（一张纸带加号的那个）。
2. 输入 `hello.c`，回车。
3. 把这个文件内容**全部**粘进去（或者跟着敲一遍，更有感觉）：

```c
#include <stdio.h>

int main(void) {
    printf("Hello, C!\n");
    return 0;
}
```

4. 按 **Ctrl + S** 保存。**未保存的文件在标签页名字旁边有一个小圆点**，保存后圆点会变成叉。

**你应该看到：** 代码是彩色的（关键字、字符串颜色不同）。这说明 C/C++ 扩展已经在工作。

> 如果你用的是记事本而不是 VS Code 写文件，保存时务必把"保存类型"改成"所有文件"，否则会存成 `hello.c.txt`。在 VS Code 里不会有这个问题，但仍要注意名字一定要带 `.c`。

### 1.10 第 8 步：让 VS Code 会编译（tasks.json）

我们要告诉 VS Code："当我说'编译'的时候，你去执行那条 gcc 命令。" 这些设置写在工程里的 `.vscode` 文件夹中。

**第一步：建 `.vscode` 文件夹和 `tasks.json` 文件**

1. 在左侧文件列表的空白处（或者对着 `C-COURSE` 那一行）**右键 → 新建文件夹**，输入这个名字：

```text
.vscode
```

   **注意开头那个点不能省**，它是名字的一部分。

2. 在 `.vscode` 上**右键 → 新建文件**，输入 `tasks.json`，回车。

**第二步：粘内容**

把编辑器里的空内容替换成下面这份（**全选 → 删除 → 粘贴**）：

```json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "build",
      "type": "shell",
      "command": "gcc",
      "args": [
        "-fdiagnostics-color=always",
        "-std=c17",
        "-Wall",
        "-Wextra",
        "-g",
        "-o",
        "${fileDirname}\\${fileBasenameNoExtension}.exe",
        "${file}"
      ],
      "options": {
        "cwd": "${fileDirname}"
      },
      "problemMatcher": ["$gcc"],
      "group": {
        "kind": "build",
        "isDefault": true
      },
      "detail": "编译当前打开的这个 .c 文件"
    },
    {
      "label": "run",
      "type": "shell",
      "command": "\"${fileDirname}\\${fileBasenameNoExtension}.exe\"",
      "options": {
        "cwd": "${fileDirname}"
      },
      "dependsOn": "build",
      "problemMatcher": []
    }
  ]
}
```

按 **Ctrl + S** 保存。

**粘贴后的自查（很重要）：** 看里面的引号是不是英文的直引号 `"`。有些网页复制的代码会带成中文弯引号 `“ ”`，JSON 会直接报错。如果右下角弹出"JSON 中不允许注释/意外的字符"，多半就是这个原因。

**第三步：试试编译**

按 **Ctrl + Shift + B**。底部会弹出一个"终端"面板，你应该看到类似：

```text
> Executing task: gcc -fdiagnostics-color=always -std=c17 -Wall -Wextra -g -o C:\code\c-course\hello.exe C:\code\c-course\hello.c

 *  Terminal will be reused by tasks, press any key to close it.
```

同时左侧的文件列表里会多出一个 **`hello.exe`**，这就是编译出来的程序。

**如果底部出现红色报错**，去[第 11 章](#11-报错排查手册按现象找答案)对照现象。绝大多数是三类：`gcc` 找不到（PATH）、JSON 引号写错、代码本身有语法错。

**这个 json 每一行是什么意思？** 先不用管，[第 7 章](#7-vs-code-三个配置文件逐字段详解)会逐字段讲。

### 1.11 第 9 步：让 VS Code 会调试（launch.json）

**调试**的意思是：让程序跑到某一行停下来，把当时的变量值摊开给你看。这是本文最值得学的一项能力。

1. 在 `.vscode` 上**右键 → 新建文件**，输入 `launch.json`，回车。
2. 粘贴下面内容：

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "调试当前文件 (gdb)",
      "type": "cppdbg",
      "request": "launch",
      "program": "${fileDirname}\\${fileBasenameNoExtension}.exe",
      "args": [],
      "stopAtEntry": false,
      "cwd": "${fileDirname}",
      "environment": [],
      "console": "integratedTerminal",
      "MIMode": "gdb",
      "miDebuggerPath": "C:/mingw64/bin/gdb.exe",
      "setupCommands": [
        {
          "description": "为 gdb 启用整齐打印",
          "text": "-enable-pretty-printing",
          "ignoreFailures": true
        }
      ],
      "preLaunchTask": "build"
    }
  ]
}
```

3. **必须检查一行**：`"miDebuggerPath": "C:/mingw64/bin/gdb.exe"`。这是告诉 VS Code 去哪找调试器。如果你的 MinGW 装在别的地方（比如 MSYS2 的 `C:\msys64\ucrt64\bin\gdb.exe`），这里要改成你的实际路径。
   注意这里用的是**正斜杠 `/`**，不是反斜杠，也不是双反斜杠。

4. 按 **Ctrl + S** 保存。

**快速测试：** 在 `hello.c` 里，把鼠标移到 `printf` 那一行的行号**左边一点点**，会出现一个淡淡的红点，**点一下**，红点变实心 —— 这就是**断点**。然后按 **F5**。程序会自动先编译，再启动，然后停在断点上。

**你应该看到：** 左侧出现一块面板，上面有"变量"（会显示 `argc`、`argv` 之类），下面有"调用堆栈"。中间编辑器里，停住的那一行会高亮。

停住以后，试着按 **F10**（单步跳过）：程序会往下走一行，变量区会有变化。按 **Shift + F5** 结束调试。

> 如果 F5 报错说找不到 gdb，先看[第 11 章](#11-报错排查手册按现象找答案)里 "Unable to start debugging" 那一条。

### 1.12 第 10 步：消掉红波浪线（c_cpp_properties.json）

**先说清楚：能编译成功，但代码里有红波浪线，这不影响程序运行。** 那是 VS Code 的"聪明提示"（IntelliSense）在说"我不知道这个头文件在哪"，它不是编译器的报错。

1. 在 `.vscode` 上**右键 → 新建文件**，输入 `c_cpp_properties.json`，回车。
2. 粘贴：

```json
{
  "configurations": [
    {
      "name": "Win32",
      "includePath": ["${workspaceFolder}/**"],
      "defines": [],
      "compilerPath": "C:/mingw64/bin/gcc.exe",
      "cStandard": "c17",
      "cppStandard": "c++17",
      "intelliSenseMode": "windows-gcc-x64"
    }
  ],
  "version": 4
}
```

3. 同样检查 `compilerPath` 是不是你的实际路径（正斜杠）。
4. 保存。红波浪线一般几秒内消失；如果还在，按 **Ctrl + Shift + P** 打开命令面板，输入 `C/C++: Reset IntelliSense Database` 执行一次。

### 1.13 第 1 章做完，你的目录应该长这样

```text
C:\code\c-course\
├── .vscode\
│   ├── tasks.json              ← 怎么编译（调用 gcc）
│   ├── launch.json             ← 怎么调试（调用 gdb）
│   └── c_cpp_properties.json   ← 编辑器怎么提示（IntelliSense）
├── hello.c
└── hello.exe                   ← 编译产物，会不断被覆盖
```

**日常使用的三个动作，现在就可以记住：**

| 我想干嘛 | 按键 / 操作 |
| --- | --- |
| 编译 | **Ctrl + Shift + B** |
| 调试（会自动先编译） | **F5** |
| 在终端里手动运行 | 按 **Ctrl + `** 打开终端，输入 `.\hello.exe` |

**把第 1 章验收一遍**（每条都打勾再往下走）：

- [ ] 新终端里 `gcc --version`、`g++ --version`、`gdb --version` 都能出版本号
- [ ] `where.exe gcc` 指向 `C:\mingw64\bin\gcc.exe`
- [ ] `C:\mingw64\bin\gcc.exe` 这个文件真实存在
- [ ] VS Code 是"打开文件夹"打开的 `C:\code\c-course`（左侧显示 C-COURSE）
- [ ] **Ctrl + Shift + B** 能编译出 `hello.exe`
- [ ] **F5** 能在断点处停下
- [ ] 断点停下时，左侧能看到变量值
- [ ] `.vscode` 里有三个 json 文件

八条全勾上，环境就算配好了。**如果现在还有哪步没成，先别继续，去[第 11 章](#11-报错排查手册按现象找答案)按现象查。**

## 2. 一分钟原理：刚才那些操作到底在干什么

如果你只想知道"为什么这么配"，看完这一章就够了。想深挖再往后面翻。

### 2.1 你在跟四个程序打交道

Dev-C++ 之类的"集成环境"把这些藏起来了，所以很多人用了四年还是不知道自己在干什么。本文把它们拆开：

| 角色 | 在本方案里是谁 | 它干什么 | 没它会怎样 |
| --- | --- | --- | --- |
| 编辑器 | VS Code | 打字、高亮、跳转、补全 | 没地方舒服地写代码 |
| 编译器 | `gcc.exe`（来自 MinGW-w64） | 把 `.c` 翻译成 `.exe` | 点了"编译"没反应 |
| 调试器 | `gdb.exe` | 下断点、单步、看变量和调用栈 | 只能靠到处 `printf` 猜 |
| 构建系统 | `mingw32-make` / VS Code 的任务 | 决定先编谁、后编谁、传什么参数 | 多个 `.c` 文件不知道怎么一起编 |

一句话：**VS Code 不会编译 C。** 你按 Ctrl + Shift + B 时，是 VS Code 照着 `tasks.json` 替你敲了一行命令：

```text
gcc -g -Wall -std=c17 -o hello.exe hello.c
```

`tasks.json` 就是"刚才那行命令"的可视化版本。理解这一点，这一章就值了。

### 2.2 PATH 是 Windows 的通讯录

Windows 里说"运行 gcc"，系统并不知道 `gcc.exe` 在哪。它会翻一份名单（PATH），一个目录一个目录地找，找到就叫这个程序跑起来。没登记，它只能告诉你"没有这个命令"。

所以：

- 第 3 步做的事 = 把 `C:\mingw64\bin`（`gcc.exe` 住的文件夹）登记进名单。
- 登记完必须**重开终端**：程序启动时会复制一份当时的环境变量，已经开着的终端拿的是旧名单。

### 2.3 三个 json 各管一件互不相干的事

| 文件 | 管什么 | 谁在用 |
| --- | --- | --- |
| `.vscode/tasks.json` | **怎么编译**：调哪个命令、传什么参数 | 你按 Ctrl + Shift + B 时 |
| `.vscode/launch.json` | **怎么调试**：启动哪个 exe、用哪个 gdb、先跑哪个任务 | 你按 F5 时 |
| `.vscode/c_cpp_properties.json` | **编辑器怎么提示**：头文件在哪、按哪个标准 | VS Code 的红波浪线、跳转、补全 |

它们**互不依赖**：删掉 `c_cpp_properties.json`，编译和调试照常；只留 `tasks.json` 也能编译，只是按 F5 没反应。

### 2.4 为什么装 MinGW-w64 而不是别的

一句话版本：**它和 Linux 上的 gcc 是同一套东西**，命令行一致、教材一致、以后上服务器不用重新学；而且免安装、体积小。MSVC 要装十几 GB 的 Visual Studio，Clang 在 Windows 上配置更绕。详细对比在[第 4 章](#4-mingw-w64-是什么编译器版本和安装方式)。

### 2.5 为什么劝你别一直用 Dev-C++

不骂它，只摆事实：

1. 它把上面四个角色捆成一个黑盒，你在里面用四年，出来还是不知道 `gcc` 在哪、编译参数是什么。
2. 自带的 GCC 版本往往老得离谱，很多新语法直接不认，默认 C 标准也旧。
3. 调试器经常崩，很多人最后放弃调试，只会用 `printf` 猜 bug。
4. 它只服务 C/C++。你以后学 Python、上 Linux，这套经验一点都带不过去。

**C 语言本身没有"Dev-C++ 版本"和"VS Code 版本"之分**，编译器只认 C 标准，你交的 `.c` 源文件老师拿任何编译器都能评。所以务实的用法是：交作业听学校安排，自己写代码用本文这套（见[第 13 章](#13-如果学校强制你用-dev-c)）。

## 3. 电脑基础补课：文件、文件夹、路径、终端

这一章是给"第一次认真用 Windows"的人看的。已经会的人可以跳过，但要**在第 1 章遇到不懂的步骤时回来查**。

### 3.1 文件、文件夹、硬盘

- **文件**：一份有内容的东西，比如一张图片、一首歌、一份作业、一个程序。每个文件都有名字。
- **文件夹**（也叫"目录"）：用来装文件的"抽屉"。文件夹里还能放文件夹。
- **硬盘**：装所有东西的大柜子。一台电脑可能分成几个"盘"，最常见的是 C 盘（系统盘）和 D 盘（数据盘）。

```text
本地磁盘 (C:)\        ← 硬盘的一个分区
├── Windows\          ← 系统文件，别动
├── Program Files\    ← 软件默认装在这
├── Users\            ← "用户文件夹"，你的桌面、下载、文档都在里面
│   └── 你的名字\
│       ├── Desktop\   ← 桌面（你在桌面上看到的东西其实存在这里）
│       └── Downloads\ ← 浏览器下载的东西默认放这
└── mingw64\          ← 我们刚放进去的编译器
```

**"桌面"不是硬盘上的另一个地方**，它只是 `C:\Users\你的名字\Desktop` 这个文件夹的"快捷方式展示"。所以把东西放桌面 = 放在用户文件夹里。

### 3.2 扩展名：为什么我的文件名后面没有 `.c`

一个完整的文件名是"名字 + 点 + 扩展名"，扩展名表示它是什么类型的文件：

| 扩展名 | 是什么 |
| --- | --- |
| `.c` | C 语言源代码（我们要写的东西） |
| `.cpp` | C++ 源代码 |
| `.h` | 头文件（声明，见[第 9 章](#9-多文件工程与-makefile)） |
| `.exe` | Windows 上可以运行的程序 |
| `.zip` / `.7z` | 压缩包 |
| `.txt` | 纯文本 |
| `.json` | 一种配置/数据格式（`.vscode` 里那三个文件就是） |

**默认情况下，Windows 会把扩展名藏起来**，于是 `hello.c` 在资源管理器里显示成 `hello`。这会带来两个坑：一是你以为自己存对了，其实存成了 `hello.c.txt`；二是不知道文件夹里哪个才是真正的程序。

**让它显示出来：**

- **Windows 11**：打开任意文件夹窗口 → 顶部 **"查看"** → **"显示"** → 勾选 **"文件扩展名"**。
- **Windows 10**：打开任意文件夹窗口 → 顶部 **"查看"** 选项卡 → 勾选 **"文件扩展名"**。

显示后，你会看到 `gcc.exe`、`hello.c`、`hello.exe` 的完整名字。**建议现在就打开这个开关**，后面排查问题方便得多。

### 3.3 路径：`C:\code\c-course\hello.c` 是什么

**路径就是"这个文件的地址"**，从最外层一路写到文件本身：

```text
C:\code\c-course\hello.c
│  │     │        └─ 文件名（hello，扩展名 .c）
│  │     └────────── 它所在的文件夹（c-course）
│  └──────────────── c-course 所在的文件夹（code）
└─────────────────── 盘符：C 盘（冒号是盘符的一部分）
```

几个必须知道的规则：

- **`\` 和 `/` 是同一个意思的两种写法**，都表示"进到下一层"。Windows 传统上用 `\`，网址和配置文件里常用 `/`。所以 `C:\mingw64\bin` 和 `C:/mingw64/bin` 指的是同一个文件夹。
- 但在 **JSON 配置**里，`\` 有特殊含义（它是"转义符"），所以写单个 `\` 会报错。这也是为什么 `launch.json` 里写的是 `C:/mingw64/bin/gdb.exe`（正斜杠），或者写成双反斜杠 `C:\\mingw64\\bin`。详见[第 7 章](#7-vs-code-三个配置文件逐字段详解)。
- 路径最后不要自己加 `\`：`C:\mingw64\bin` 就够了。
- **`..` 表示上一层**，**`.` 表示当前目录**。所以 PowerShell 里运行当前文件夹的程序要写 `.\hello.exe`。

**路径分两种：**

- **绝对路径**：从盘符写起，比如 `C:\code\c-course\hello.c`。任何情况下都能唯一定位一个文件。
- **相对路径**：从"当前所在的位置"写起，比如 `hello.c`、`.\sub\a.c`。它依赖你现在站在哪个文件夹里。

### 3.4 文件资源管理器怎么用（几个能省半小时的技巧）

按 **Win + E** 打开它，左侧是"快速访问"和"此电脑"，右侧是内容。

1. **地址栏可以直接粘贴路径。** 点一下地址栏，把 `C:\mingw64\bin` 粘进去回车，直接到达。比一层层双击快得多。
2. **复制一个文件的完整路径**：按住 **Shift** 在文件上**右键**，菜单里会多出 **"复制文件地址"**，点一下就复制了完整路径（注意它可能自带引号，粘到配置里要检查）。
3. **后退/前进**：窗口左上角的箭头，或者按 **Alt + ←**。
4. **显示/隐藏**：看不到文件时，点"查看"→ 勾选"隐藏的项目"。

### 3.5 下载、解压、复制与剪切

- **下载的东西在哪？** 一般在 `C:\Users\你的用户名\Downloads`。浏览器里按 **Ctrl + J** 能打开下载列表，右侧有"在文件夹中显示"。
- **压缩包**：`.zip` 可以被 Windows 直接打开（右键 → 全部解压缩…）；**`.7z`、`.rar` 以及分卷压缩包，自带功能都打不开**，需要装一个第三方解压软件。本文推荐 **Bandizip**，装法见下一节 [3.6](#36-装一个顺手的解压软件bandizip)。
- **解压时会多出一层文件夹**，这是正常的。解压后要进去看一眼，确认结构对不对（比如确认 `mingw64\bin\gcc.exe` 存在）。
- **复制（Ctrl + C）vs 剪切（Ctrl + X）**：复制会保留原文件（相当于"复印一份"），剪切是"搬走"。**移动大文件夹用剪切更省时间**，也不占额外空间。
- **同名文件夹粘贴时会问"合并/替换"**：选"替换目标中的文件"是覆盖，谨慎使用；不确定就先取消，把旧文件夹改个名。

### 3.7 终端是什么？和"双击图标"有什么区别

**终端**（也叫命令行、控制台、命令提示符、PowerShell、CMD）是一个"用打字来指挥电脑"的窗口。它看起来吓人，其实规则很简单：

- 你输入一行命令，按回车，它执行，然后把结果显示在下面。
- 结果可能是"什么都没打印"（这通常代表成功），也可能是一段报错。
- **看不懂输出没关系**，重点是找到里面带 `error` 的那几行。

Windows 上你会遇到三种终端，命令基本通用：

| 名字 | 怎么打开 | 提示符长这样 | 特点 |
| --- | --- | --- | --- |
| **Windows PowerShell** | Win + X → 终端 / Windows PowerShell | `PS C:\Users\你>` | Win10/11 默认，功能多 |
| **命令提示符（cmd）** | Win + R → 输入 `cmd` → 回车 | `C:\Users\你>` | 最老，命令略少 |
| **VS Code 集成终端** | 在 VS Code 里按 **Ctrl + `** | 同上，但已经在你打开的文件夹里 | 后面主要用它 |

**几条保命操作：**

- **粘贴**：**Ctrl + V** 就可以；如果不行，在终端窗口里**右键**也会粘贴。
- **复制输出**：用鼠标选中文字，按回车或 Ctrl + C（在终端里 Ctrl + C 有时是"中断"的意思，选中内容后再按才安全）。
- **中断正在跑的命令**：按 **Ctrl + C**（比如程序卡在等你输入）。
- **清屏**：输入 `cls` 回车。
- **翻历史命令**：按 **↑** 上箭头，可以找回上一条命令。
- **补全路径**：输入前几个字母按 **Tab**，会自动补全文件名（很好用，但也容易按出意外结果，注意看补出来的对不对）。
- **命令从哪里来**：要么是终端自带的（如 `cd`、`cls`、`mkdir`），要么是 PATH 里登记过的程序（如 `gcc`），要么是你明确写了路径的（如 `.\hello.exe`、`C:\mingw64\bin\gcc.exe`）。

**为什么终端和 VS Code 都要"重开"才能看到新装的程序**：见[第 5 章](#5-path-环境变量windows-的通讯录)。

### 3.8 为什么路径里不要有中文和空格

这是新手最容易忽略的两个坑，但非常真实：

1. **空格会被当成参数分隔符。** 命令 `gcc -o C:\My Code\a.exe a.c` 里，`C:\My` 和 `Code\a.exe` 会被理解成两个不同的东西，报错信息还很难懂。所以要给整条路径加引号，而新手很难记得每次都加。
2. **中文路径依赖编码。** 有的工具链、脚本、Makefile 在处理非英文路径时会乱码或直接失败（尤其是旧版本工具和老式构建脚本）。
3. **很多教材、示例、命令默认英文路径**，你复制过来就能用；一旦路径带空格或中文，就得自己改，出错概率直线上升。

所以本文从头到尾都让你用 `C:\mingw64` 和 `C:\code\c-course`：**没有空格，没有中文**。如果 Windows 用户名是中文（比如 `C:\Users\小明`），这也不是世界末日，但请尽量把代码和工具放在 C 盘根目录下的英文路径里。

### 3.9 权限、弹窗和杀毒软件

- **UAC 弹窗**：那个"你要允许此应用对你的设备进行更改吗？"的蓝屏，是 Windows 在问你要不要给它管理员权限。装 VS Code 时会弹，点"是"。改 PATH（用户变量）不会弹。
- **SmartScreen**：从网上下的安装包第一次运行时，可能出现"Windows 已保护你的电脑"，点"更多信息"→"仍要运行"。
- **杀毒软件误报**：`gcc.exe`、`gdb.exe` 这类编译工具偶尔会被误报（尤其是第三方杀软）。如果出现"编译到一半文件被删/被拦"，把 `C:\mingw64` 加进白名单：
  - **Windows 安全中心** → 病毒和威胁防护 → 管理设置 → 排除项 → 添加或删除排除项 → 添加排除项 → **文件夹** → 选 `C:\mingw64`。
- **文件被占用**：如果编译时报 `Permission denied`，通常是你上次运行的程序还没关（或者调试会话没结束）。关掉那个黑窗口再编译。

## 4. MinGW-w64 是什么：编译器、版本和安装方式

### 4.1 编译器到底在干什么

你用记事本写的是**给人看的文本**，电脑的 CPU 只认识**机器指令**。编译器就是那个翻译：把你的 `.c` 变成 Windows 上能双击运行的 `.exe`。这四个阶段的细节在 [6.1](#61-从-c-到-exe-的四个阶段) 里用命令演示。

严格说，`gcc` 不是一个程序，而是一个"总调度"：它会依次叫上预处理器、C 编译器本体、汇编器 `as`、链接器 `ld` 来干活。你只需要敲一条 `gcc`，它自己安排。

**好消息**：MinGW-w64 提供的就是这一整套工具，而且**命令行和 Linux 上一模一样**。你在 Windows 上学的 `gcc -Wall -g`，换到 Linux 服务器上还能用。

### 4.2 Windows 上装编译器的三个选择

| 方案 | 是什么 | 优点 | 为什么本文不选它 |
| --- | --- | --- | --- |
| **MSVC**（`cl.exe`） | Visual Studio 自带的编译器 | 和 Windows 贴合最好、优化强、调试体验好 | 要装十几 GB 的 Visual Studio；参数风格（`/W4`、`/Fe`）和教材、OJ 完全不同 |
| **Clang / LLVM** | 苹果主推的编译器前端 | 报错信息友好、工具链现代 | 在 Windows 上原生配置更绕，对新手性价比不高 |
| **MinGW-w64**（GCC） | 把 GCC 移植到 Windows | 命令行和 Linux 一致、轻量、免费、和大多数教材一致 | ——本文的选择 |

> 顺带说一句：`gcc` 是 C 编译器，`g++` 是 C++ 编译器，Windows 上它们由同一套 MinGW-w64 提供。你写 `.c` 时用 `gcc`；写 C++ 时把命令里的 `gcc` 换成 `g++`、把 `-std=c17` 换成 `-std=c++17` 或更新，其余参数含义一样。

### 4.3 一个特别容易踩的历史坑：MinGW ≠ MinGW-w64

| 名字 | 官网 | 状态 |
| --- | --- | --- |
| **MinGW**（老） | mingw.org | 停在很老的 GCC 版本，只支持 32 位，基本不再更新 |
| **MinGW-w64**（新） | mingw-w64.org | 支持 64 位，持续更新，就是本文要的 |

两个名字只差一个 `-w64`，搜索引擎经常把你带到前一个。所以无论从哪下载，**认准名字里有 `mingw-w64`、架构是 `x86_64`**。

还有个容易困惑的地方：装完之后，`bin` 目录里有一个 `x86_64-w64-mingw32-gcc.exe`，也有一堆 `gcc.exe`。后者是前者的副本（或指向它的符号链接/硬链接），名字短、方便敲。**你只需要用 `gcc`。**

**再理清一个概念**：MSYS2 和 MinGW-w64 不是竞争关系。MSYS2 是一个"装在 Windows 上的小 Linux 环境 + 包管理器（pacman）"，它负责**下载和打包**；MinGW-w64 是**工具链本身**。用 MSYS2 装出来的 `C:\msys64\ucrt64\bin\gcc.exe` 就是原生 Windows 程序。

### 4.4 WinLibs 的文件名逐段解读

本文主推 WinLibs 是因为它**免安装**：解压即用，卸载就是删文件夹，不写注册表、不需要管理员权限。

```text
winlibs-x86_64-posix-seh-gcc-15.2.0-mingw-w64ucrt-13.0.0-r1.zip
        └────┬────┘└─┬──┘└┬─┘└────┬─────┘└────────┬────────┘└┬┘
           CPU 架构  线程  异常   GCC 版本   运行时/发行版  修订号
```

| 字段 | 可能取值 | 怎么选 |
| --- | --- | --- |
| CPU 架构 | `x86_64` / `i686` | 现在的电脑都选 `x86_64`（64 位）；只有确实查到自己是 32 位系统才选 `i686` |
| 线程模型 | `posix` / `win32` | 选 `posix`：对 C++ 标准库的线程、互斥量支持更好 |
| 异常处理 | `seh` / `dwarf` / `sjlj` | 64 位选 `seh`（快且干净）；`dwarf`/`sjlj` 是 32 位时代的老方案 |
| 运行时 | `ucrt` / `msvcrt` | 选 `ucrt`：Windows 10 之后的现代 C 运行库；`msvcrt` 更老但兼容旧系统 |
| GCC 版本 | `gcc-15.x` 等 | 越新越好，但不必追最新，能用就行 |
| 修订号 | `r1` / `r2` … | 同一版本的小修补，选大的 |

**UCRT 和 MSVCRT 到底差在哪？** 它们是 C 标准库的两代实现。`ucrt`（Universal C Runtime）从 Windows 10 开始是系统自带组件，行为和 Linux 上的 glibc 更接近；`msvcrt` 是很老的实现（还能上 Windows Vista/7）。你如果只在 Win10/11 上写作业，选 `ucrt`。

WinLibs 的下载页通常还分 `.zip` 和 `.7z` 两种打包：

- **选 `.zip`**：Windows 能直接解压，省一步。
- `.7z` 体积小一点，但 Windows 自带功能打不开；按[第 3.6 节](#36-装一个顺手的解压软件bandizip)装了 Bandizip 之后，两种格式随便选。

### 4.5 方案 B：MSYS2（想要"命令行装包"就选它）

WinLibs 是"下载压缩包"路线；MSYS2 是"包管理器"路线，适合以后想装 CMake、SDL2、OpenSSL 这类库的人，因为 `pacman` 能把它们一起管起来。

1. 到 [msys2.org](https://www.msys2.org/) 下载安装包并安装，默认路径 `C:\msys64`。
2. 从开始菜单打开 **"MSYS2 UCRT64"**（注意不是那个叫 "MSYS2 MSYS" 的）。
3. 在这个终端里执行：

```bash
pacman -Syu
```

   如果它提示要关闭终端，就关掉重开，再执行一次 `pacman -Syu`。

4. 然后安装工具链：

```bash
pacman -S mingw-w64-ucrt-x86_64-toolchain
```

   提示 `Enter a selection (default=all)` 时**直接回车**，它会装上 `gcc`、`g++`、`gdb`、`make` 等一整套。

5. 回到[第 1 章第 3 步](#1-照做就行从零到跑出-hello-world)那样加 PATH，但要填的是：

```text
C:\msys64\ucrt64\bin
```

| 看起来很像的目录 | 能不能加进 PATH |
| --- | --- |
| `C:\msys64\ucrt64\bin` | ✅ 正确的，原生 Windows 程序 |
| `C:\msys64\mingw64\bin` | 旧版 MSYS2 的对应目录，也有人用；建议统一用 ucrt64 |
| `C:\msys64\usr\bin` | ❌ 别加。这里的程序跑在 MSYS2 模拟环境里，编出来的 exe 可能依赖 `msys-2.0.dll`，拿到别的电脑上跑不了 |

> 用 MSYS2 时，make 的名字是 `make`（不是 `mingw32-make`），`mingw32-make` 和它是同一个东西。

### 4.6 方案 C：winget / scoop（可选）

如果你已经习惯用包管理器，可以图省事：

```powershell
winget install Microsoft.VisualStudioCode
winget install MSYS2.MSYS2
```

WinLibs 的 winget 包名各版本可能不同，**先搜再装，不要照抄**：

```powershell
winget search winlibs
```

scoop 用户可以先 `scoop search mingw` 看看有没有合适的包（包名会变，以搜索结果为准）。

> 不过对新手，我还是建议**第一次手动走一遍方案 A**。你会亲眼知道 `gcc.exe` 住在哪、PATH 里写了什么，这对以后排查问题帮助极大。包管理器的方便是以"你不知道它干了什么"为代价的。

### 4.7 装在哪个目录、怎么升级、怎么卸载

- **位置**：`C:\mingw64`（WinLibs）或 `C:\msys64`（MSYS2）。
- **升级（WinLibs）**：下载新版本的 zip → 解压 → 把旧的 `C:\mingw64` 改名备份 → 把新的放到原位。**升级前一定要关掉 VS Code 和所有终端**，否则 `gcc.exe` 正被占用，没法替换。
- **升级（MSYS2）**：打开 "MSYS2 UCRT64"，执行 `pacman -Syu`。
- **卸载（WinLibs）**：删掉 `C:\mingw64`，再回[第 1 章第 3 步](#1-照做就行从零到跑出-hello-world)把 PATH 里那一行删掉。
- **查看装了什么版本**：`gcc --version`、`gdb --version`、`where.exe gcc`。

## 5. PATH 环境变量：Windows 的"通讯录"

这一章解释第 1 章第 3 步到底干了什么。**它是新手出错最多的一步**，值得读完。

### 5.1 什么是环境变量

**环境变量**是 Windows 给每个程序准备的一份"小纸条"，上面写着一些全局设置。程序启动时会拿到这份纸条，知道：临时文件夹在哪、系统盘是哪个、**以及去哪些目录找命令**。

`PATH` 就是其中最重要的一条。它的值是一串目录路径，用分号隔开：

```text
C:\Windows\system32;C:\Windows;C:\Program Files\Git\cmd;C:\mingw64\bin
```

你在终端里敲 `gcc`，系统就按这个顺序一个个目录去找 `gcc.exe`：

```text
在 C:\Windows\system32 找？ 没有
在 C:\mingw64\bin 找？       找到了 → 执行它
全找完还是没有 → 报"不是内部或外部命令"
```

**所以"加 PATH"= 把 `gcc.exe` 所在的文件夹告诉 Windows。**

注意一个细节：**PATH 里登记的是"文件夹"，不是"文件"。** 写 `C:\mingw64\bin` 对，写 `C:\mingw64\bin\gcc.exe` 错。

### 5.2 "用户变量"和"系统变量"选哪个

`环境变量` 窗口分上下两半：

| | 上半部分：用户变量 | 下半部分：系统变量 |
| --- | --- | --- |
| 作用范围 | 只对你这一个用户生效 | 对这台电脑所有用户生效 |
| 需要管理员权限 | 不需要 | 需要 |
| 出问题的风险 | 低（改坏了只影响自己） | 高（改坏了系统里别的软件一起坏） |
| 本文建议 | ✅ 改这个 | ❌ 别动 |

它们的 PATH 会**合并**：系统 PATH 在前，用户 PATH 在后。所以如果系统 PATH 里也有一套 GCC（比如你以前装过 CodeBlocks），它可能抢先被找到 —— 见 [5.5](#55-why-multiple-gcc)。

### 5.3 为什么不要用命令行 `setx` 改 PATH

网上很多教程教你：

```powershell
setx PATH "%PATH%;C:\mingw64\bin"
```

**请不要这么做**，两个原因：

1. **`setx` 会把值截断在 1024 个字符。** PATH 一长就直接损坏，后半截全丢——这种损坏很难发现，后果是别的软件莫名其妙找不到命令。
2. 它会把当时的"系统 PATH + 用户 PATH"合并后的结果**整体写进用户 PATH**，于是系统变量里的内容被复制进用户变量，越滚越长、越来越乱。

用图形界面一步步点，多花 30 秒，但绝对安全。

### 5.4 为什么加完必须"新开终端"

环境变量是**程序启动时复制一份**的，不是实时读取的。你在图形界面里改完 PATH 时：

- 已经开着的终端、VS Code：手里还是**改之前的旧纸条**，怎么试都找不到 `gcc`。
- 之后新开的终端、新启动的 VS Code：拿到**新纸条**，一切正常。

所以规则是：**改完 PATH，关掉所有终端和 VS Code，重新打开。** 这一条不照做，就会得到全文最常见的那句报错：

```text
gcc : 无法将“gcc”项识别为 cmdlet、函数、脚本文件或可运行程序的名称。
```

> VS Code 还有一个坑：如果你只关掉了 VS Code 的窗口，但托盘里/后台还有 VS Code 进程没退，它可能仍拿着旧环境。实在不放心就重启电脑一次，彻底干净。

### 5.5 <a id="55-why-multiple-gcc"></a>为什么 `where.exe gcc` 可能指向"别的地方"

`where.exe gcc` 会把**所有**在 PATH 里找到的 `gcc.exe` 都列出来，第一个就是要被执行的那个。如果输出是：

```text
C:\Program Files\CodeBlocks\MinGW\bin\gcc.exe
C:\mingw64\bin\gcc.exe
```

说明你以前装过另一套 GCC，而且它在 PATH 里的位置更靠前。**你敲 `gcc` 实际用的是老的那一套**（版本旧、可能缺少 gdb），而你在 VS Code 里配的 `compilerPath` 又指向新的，两边不一致，就会出现"命令行能编、VS Code 报奇怪的错"。

**处理办法（二选一）：**

1. 把旧的那一行从 PATH 里删掉（在同样的"编辑环境变量"窗口里选中 → 删除）；
2. 或者把 `C:\mingw64\bin` 移到更前面（列表里选中它，用右侧"上移"按钮；Win11 的编辑器里有"上移/下移"）。

改完记得**重开终端**再 `where.exe gcc` 确认。

### 5.6 PATH 出问题时的自查清单

按顺序做：

1. **终端是不是新开的？** 关掉重开。
2. **`C:\mingw64\bin\gcc.exe` 这个文件真的存在吗？** 在资源管理器地址栏粘贴 `C:\mingw64\bin` 回车看一眼。不存在 → 第 1 章第 2 步没做对（多半是目录套娃）。
3. **PATH 里那一行写对了吗？** 必须是 `C:\mingw64\bin`，不能有引号、不能有分号、不能指向文件本身。
4. **PATH 加在"用户变量"里了吗？** 加在系统变量里也能用，但你得确认保存成功了。
5. **有没有第二套 GCC 抢占？** 用 `where.exe gcc` 看，参考 [5.5](#55-why-multiple-gcc)。
6. **当前终端的 PATH 里到底有什么？** 直接在终端里输入下面的命令查看：

```powershell
# PowerShell
$env:Path -split ';'
```

```cmd
:: 命令提示符
path
```

逐行扫一眼有没有 `C:\mingw64\bin`。没有就说明你改的不是当前用户/没保存成功。

### 5.7 四种"看起来加了，其实没加"的写法

| 写法 | 为什么错 |
| --- | --- |
| `C:\mingw64\bin\gcc.exe` | 登记的是文件夹，不是文件 |
| `"C:\mingw64\bin"` | 引号是多余的，某些情况下会导致查找失败 |
| `C:\mingw64\bin;` | 结尾的分号是分隔符，不是路径的一部分；图形界面里不需要自己写分号 |
| `C:mingw64\bin` | 少了 `\`，这不是一个合法的绝对路径 |

## 6. gcc 与编译参数：那一行命令到底做了什么

### 6.1 从 `.c` 到 `.exe` 的四个阶段

你在 VS Code 里按一下 Ctrl + Shift + B，背后是四个阶段。想亲眼看到中间产物，可以在 `C:\code\hello` 里试：

```powershell
# 阶段 1：预处理（展开 #include 和 #define）
gcc -E hello.c -o hello.i

# 阶段 2：编译（生成汇编代码）
gcc -S hello.i -o hello.s

# 阶段 3：汇编（生成机器码目标文件）
gcc -c hello.s -o hello.o

# 阶段 4：链接（把目标文件和运行库拼成 exe）
gcc hello.o -o hello.exe
```

也可以让 gcc 一步做完（这就是平时用的方式）：

```powershell
gcc hello.c -o hello.exe
```

**强烈建议试一次 `gcc -E hello.c -o hello.i`，然后用 VS Code 打开 `hello.i`。** 你会发现几行代码变成了几万行——因为 `#include <stdio.h>` 把整个标准输入输出的声明都"复制"进来了。这一刻你会真正理解"头文件"是什么。

| 阶段 | 输入 | 输出 | 谁在干 |
| --- | --- | --- | --- |
| 预处理 | `.c` | `.i` | 展开宏、包含头文件、处理条件编译 |
| 编译 | `.i` | `.s` | 翻译成汇编 |
| 汇编 | `.s` | `.o`（Windows 上也叫 `.obj`） | 汇编器 `as` |
| 链接 | `.o` + 库 | `.exe` | 链接器 `ld` |

**编译期错误**发生在阶段 1–2（语法错误、函数写错）；**链接期错误**发生在阶段 4（函数声明了但没实现）。这两类错误的提示长相不同，[6.7](#67-link-errors) 会讲。

### 6.2 那条 gcc 命令逐段拆开

```text
gcc -std=c17 -Wall -Wextra -g -o hello.exe hello.c
 │      │       │      │    │    │          └── 要编译的源文件
 │      │       │      │    │    └───────────── -o 后面的名字 = 生成的文件
 │      │       │      │    └────────────────── -g：生成调试信息（gdb 需要）
 │      │       │      └─────────────────────── -Wextra：再打开一批额外警告
 │      │       └────────────────────────────── -Wall：打开常见警告
 │      └────────────────────────────────────── -std=c17：按 C17 标准编译
 └───────────────────────────────────────────── 编译器程序本身
```

阅读顺序建议反过来：**先看最后的源文件，再看 `-o` 输出，然后才是那一堆开关。**

### 6.3 常用参数表

| 参数 | 作用 | 什么时候用它 |
| --- | --- | --- |
| `-std=c17` | 指定 C 语言标准（也可写 `-std=c18`） | 平时写作业都带上；不写就用 gcc 默认标准，很多新语法可能不认 |
| `-Wall` | 打开常见警告 | **建议永远打开** |
| `-Wextra` | 打开更多细节警告 | 建议永远打开 |
| `-Werror` | 把警告当成错误，不修不让过 | 想逼自己写干净代码时用；初学可以先不开 |
| `-g` | 生成调试信息 | **调试必须有**，否则 gdb 看不到行号和变量名 |
| `-O0` | 不优化（默认） | 调试时用 |
| `-O1` / `-O2` / `-O3` | 不同等级的优化 | 发布/交性能作业时用；**不要用 `-O2` 调试** |
| `-o 名字` | 指定输出文件名 | 不写的话默认生成 `a.exe`，目录里会堆一堆同名文件 |
| `-c` | 只编译成 `.o`，不链接 | 多文件工程用（见[第 9 章](#9-多文件工程与-makefile)） |
| `-I 目录` | 额外到哪个目录找头文件 | 用了第三方库时 |
| `-L 目录` / `-l名字` | 到哪找库 / 链接哪个库 | 用了第三方库时（如 `-lm` 链接数学库） |
| `-finput-charset=UTF-8` | 源文件按什么编码读 | 解决中文乱码（[第 8 章](#8-中文乱码与文件编码)） |
| `-fexec-charset=GBK` | 字符串按什么编码写进 exe | 解决中文乱码（[第 8 章](#8-中文乱码与文件编码)） |
| `-v` | 打印详细过程（包括它调用了谁） | 想看看 gcc 到底干了什么 |
| `--version` | 打印版本 | 检查安装 |

一个实在的建议：**把 `-Wall -Wextra` 常开。** 学校里很多 bug（变量没初始化、数组越界、`=` 和 `==` 写反、`scanf` 传错指针）gcc 早就替你看出来了，只是很多人从来没见过那些警告。

### 6.4 `-g` 和 `-O2` 的恩怨

- `-g` 让编译器**额外记录**"这一行机器码对应源码哪一行、变量叫什么名字、放在哪"。没有它，gdb 就像一个没有地图的导航。
- `-O2` 会让编译器**重排、合并、删掉它认为没用的代码**。于是：变量可能被塞进寄存器、循环可能被改写、你以为存在的中间变量可能"消失"。

**结论：调试就用 `-g -O0`。** 如果你在调试时看到"变量已被优化掉"或者变量值莫名其妙，先检查自己是不是开了优化。发布性能测试的时候再用 `-O2`。

### 6.5 头文件、`#include <...>` 和 `#include "..."`

- **头文件（`.h`）**：里面放"声明"——告诉编译器"有这么一个函数，它长这样"。
- **源文件（`.c`）**：里面放"实现"——函数真正干什么。
- 这样别的文件只要包含声明就能用这个函数，链接器最后负责把它们接上。

两种 `#include` 的区别：

```c
#include <stdio.h>    // 尖括号：在"系统头文件目录"里找（MinGW 自带的）
#include "my.h"       // 引号：先在"当前源文件所在目录"找，找不到再去系统目录
```

想知道系统头文件在哪？可以执行：

```powershell
gcc -E -v -x c nul
```

输出里会有一段 `#include <...> search starts here:`，下面列的就是它找头文件的目录（通常是 `C:\mingw64\include`、`C:\mingw64\x86_64-w64-mingw32\include` 之类）。**不用背，知道有这回事就行**，因为 VS Code 会自动问 gcc 要这份清单（见[第 7 章](#7-vs-code-三个配置文件逐字段详解)）。

### 6.6 怎么读 gcc 的报错

看个例子：

```text
hello.c: In function 'main':
hello.c:5:12: error: 'printf' undeclared (first use in this function)
    5 |     printf("hi");
      |            ^~~~~~
```

逐段读：

| 部分 | 含义 |
| --- | --- |
| `hello.c` | 出问题的是这个文件 |
| `In function 'main'` | 出在 `main` 函数里 |
| `5:12` | **第 5 行、第 12 列**（列可以忽略，鼠标点一下就能跳过去） |
| `error:` | 严重程度。`error` 必须修；`warning` 是提醒，通常也该修 |
| `'printf' undeclared` | 具体的错：printf 没声明（本例是忘了 `#include <stdio.h>`） |
| 下面带 `^~~~~~` 的那两行 | 把出错的那行源码标出来，`^` 指着具体位置 |

**读报错的三条经验：**

1. **先看第一个 `error`。** 一个错误经常引发后面十个"连带错误"，修好第一个再重新编译，往往只剩一个。
2. **`warning` 也要看。** 很多运行时的诡异问题（数组越界、返回值乱跳）在编译时就有警告提示。
3. **报错里出现的 `-W` 开头的东西**（比如 `[-Wunused-variable]`）是警告的**名字**，可以直接拿它去搜索，比搜整段报错更准。

VS Code 里更方便：`problemMatcher: ["$gcc"]` 会把这些错误解析出来显示在"问题"面板（按 **Ctrl + Shift + M**），**点一下就直接跳到出错的行**。

### 6.7 <a id="67-link-errors"></a>编译期错误和链接期错误

| | 编译期（阶段 1–2） | 链接期（阶段 4） |
| --- | --- | --- |
| 典型报错 | `syntax error`、`expected ';'`、`undeclared`、类型不匹配 | `undefined reference to 'xxx'`、`multiple definition of 'main'` |
| 常见原因 | 语法写错、忘 `#include`、拼错函数名 | 函数只声明没实现、实现所在的 `.c` 没参与编译、同一个函数定义了两次 |
| 去哪章看 | 本节 + [第 11 章](#11-报错排查手册按现象找答案) | [第 9 章：多文件工程](#9-多文件工程与-makefile) |

记忆方法：**编译期是"我读不懂你写的东西"，链接期是"我读懂了，但你让我找的东西不存在（或存在好几份）"。**

## 7. VS Code 三个配置文件逐字段详解

### 7.1 先建立一个正确的心智模型

VS Code 不是一个"项目"，它只是一个**编辑器 + 一个打开的文件夹**：

```text
VS Code 窗口
├── 你打开的文件夹（比如 C:\code\c-course）  ← "工作区（workspace）"
│   ├── .vscode\        ← 这个工程自己的设置，只对打开这个文件夹时生效
│   │   ├── tasks.json
│   │   ├── launch.json
│   │   └── c_cpp_properties.json
│   └── hello.c
└── 全局设置（改一次影响所有工程）：文件 → 首选项 → 设置
```

关键点：**`.vscode` 里的配置是"跟着文件夹走"的。** 换一个文件夹打开，就是另一套配置。这也解释了为什么必须"打开文件夹"——只打开单个 `.c` 文件时，VS Code 不知道你属于哪个工程，自然读不到 `.vscode`。

### 7.2 `tasks.json`：怎么编译

```json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "build",
      "type": "shell",
      "command": "gcc",
      "args": ["-std=c17", "-Wall", "-g", "-o", "...hello.exe", "..."],
      "options": { "cwd": "${fileDirname}" },
      "problemMatcher": ["$gcc"],
      "group": { "kind": "build", "isDefault": true },
      "detail": "编译当前打开的这个 .c 文件"
    }
  ]
}
```

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `version` | `"2.0.0"` | tasks 格式版本，照抄即可 |
| `label` | `"build"` | 这个任务的**名字**。`launch.json` 里的 `preLaunchTask` 靠它对上号，不能随便改 |
| `type` | `"shell"` | 当成一条 shell 命令执行（这样才会经过 PATH 去找 `gcc`） |
| `command` | `"gcc"` | 要执行谁。因为 PATH 里有它，所以写名字就行；写全路径也可以 |
| `args` | `["-std=c17", …]` | 传给命令的参数，一项一个字符串 |
| `options.cwd` | `"${fileDirname}"` | 在哪个目录里执行这条命令 |
| `problemMatcher` | `["$gcc"]` | 用内置的 gcc 解析器把报错变成"问题"面板里的条目 |
| `group.kind` | `"build"` | 标记为"生成任务"，这样 **Ctrl + Shift + B** 能直接跑它 |
| `group.isDefault` | `true` | 设为默认任务，才能用快捷键 |
| `dependsOn` | `"build"` | （`run` 任务用了）跑它之前先跑 `build` |
| `detail` | 字符串 | 只在任务列表里显示的说明文字，随便写 |

**参数里那两个长字符串就是路径拼接：**

```text
"${fileDirname}\\${fileBasenameNoExtension}.exe"
        │              │
        │              └── 当前文件去掉扩展名后的名字：hello
        └── 当前文件所在文件夹：C:\code\c-course
```

拼起来就是 `C:\code\c-course\hello.exe`。中间那个 `\\` 在 JSON 里表示**一个反斜杠**（因为 `\` 在 JSON 里是转义符）。你也可以整段写成 `"${fileDirname}/${fileBasenameNoExtension}.exe"`，用正斜杠，效果一样且不用双写。

### 7.3 VS Code 的内置变量

这些 `${...}` 是 VS Code 提供的变量，可以在三个 json 里通用：

| 变量 | 含义 | 在 `C:\code\c-course\hello.c` 上 |
| --- | --- | --- |
| `${file}` | 当前文件的完整路径 | `C:\code\c-course\hello.c` |
| `${fileDirname}` | 文件所在目录 | `C:\code\c-course` |
| `${fileBasename}` | 带扩展名的文件名 | `hello.c` |
| `${fileBasenameNoExtension}` | 不带扩展名的文件名 | `hello` |
| `${fileExtname}` | 扩展名 | `.c` |
| `${relativeFile}` | 相对于工作区根目录的路径 | `hello.c` |
| `${workspaceFolder}` | 打开的文件夹根目录 | `C:\code\c-course` |
| `${env:PATH}` | 当前进程的环境变量 | 一整串路径 |

**为什么要用变量而不是写死路径？** 因为写死之后，你把工程换个目录（或者拷给同学）就全废了。用变量，配置跟着工程走。

### 7.4 `launch.json`：怎么调试

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "调试当前文件 (gdb)",
      "type": "cppdbg",
      "request": "launch",
      "program": "${fileDirname}\\${fileBasenameNoExtension}.exe",
      "args": [],
      "stopAtEntry": false,
      "cwd": "${fileDirname}",
      "environment": [],
      "console": "integratedTerminal",
      "MIMode": "gdb",
      "miDebuggerPath": "C:/mingw64/bin/gdb.exe",
      "setupCommands": [
        { "description": "为 gdb 启用整齐打印", "text": "-enable-pretty-printing", "ignoreFailures": true }
      ],
      "preLaunchTask": "build"
    }
  ]
}
```

| 字段 | 含义 | 新手须知 |
| --- | --- | --- |
| `name` | 这个调试配置显示的名字 | 随便起，能看懂就行 |
| `type` | `"cppdbg"` | C/C++ 扩展提供的调试器类型，固定 |
| `request` | `"launch"` | 启动一个新程序来调试（另一种是 `attach`，附加到已运行的程序） |
| `program` | 要调试的 exe 路径 | 指向你编译出来的 `hello.exe` |
| `args` | 传给程序的命令行参数 | 比如 `["./input.txt"]` |
| `cwd` | 程序运行时的"当前目录" | 影响程序里用相对路径打开的文件 |
| `stopAtEntry` | 是否在 `main` 第一行就停 | `true` 可以看程序刚启动的样子 |
| `environment` | 额外环境变量 | 一般空着 |
| `console` | **输入输出走哪** | `"integratedTerminal"` 走 VS Code 底部终端，**`scanf` 才能读到你的键盘输入** |
| `MIMode` | `"gdb"` | 用 gdb 作为调试后端 |
| `miDebuggerPath` | gdb 的完整路径 | **必须指向真实文件**；用正斜杠；写死路径是为了防 PATH 出错时找不到 |
| `setupCommands` | 启动 gdb 时先执行的命令 | `-enable-pretty-printing` 让变量显示更易读 |
| `preLaunchTask` | **启动调试前先跑哪个任务** | 和 `tasks.json` 里的 `label` 对应 |

**最值得记的两个字段：**

- **`preLaunchTask: "build"`**：按 F5 时先自动编译一遍，所以你改了代码按 F5 一定是新结果。**漏了它就会出现"我明明改了代码，怎么还在跑旧结果"这种经典问题。**
- **`console: "integratedTerminal"`**：如果你的程序要 `scanf` 输入，缺了它就会卡住不动（旧版 cpptools 里可以改用 `"externalConsole": true`，让程序单独弹一个黑窗口）。

### 7.5 `c_cpp_properties.json`：编辑器怎么提示

```json
{
  "configurations": [
    {
      "name": "Win32",
      "includePath": ["${workspaceFolder}/**"],
      "defines": [],
      "compilerPath": "C:/mingw64/bin/gcc.exe",
      "cStandard": "c17",
      "cppStandard": "c++17",
      "intelliSenseMode": "windows-gcc-x64"
    }
  ],
  "version": 4
}
```

| 字段 | 作用 |
| --- | --- |
| `includePath` | 手动补的额外头文件目录；**因为有 `compilerPath`，这里留默认就够** |
| `compilerPath` | **最关键的一行**。VS Code 会直接问这个 gcc："你的头文件在哪？"然后自动推导出所有 include 路径 |
| `cStandard` / `cppStandard` | 告诉 IntelliSense 按哪个标准来解析（要和 `tasks.json` 里的 `-std=` 保持一致） |
| `intelliSenseMode` | 有 `windows-gcc-x64`（MinGW）、`windows-msvc-x64`（MSVC）、`linux-gcc-x64` 等，**选错会导致满屏假报错** |

**"红波浪线"和"编译报错"是两回事：**

- 红波浪线 = **IntelliSense（编辑器）** 的说法。它的判断可能过时、可能不准，最常见的就是找不到头文件。
- 编译报错 = **gcc** 的说法，它在终端/问题面板里，带文件名和行号。

判断技巧：**如果在终端里 `gcc` 编译能过，但代码里有红波浪线，那一定是 IntelliSense 的问题**，改这个 json（或执行 `C/C++: Reset IntelliSense Database`）。

### 7.7 把配置复用到新工程

`.vscode` 是普通文件夹，可以整体**复制**到新工程里，配置立刻生效。也可以做成模板：

```text
C:\code\_template\.vscode\
├── tasks.json
├── launch.json
└── c_cpp_properties.json
```

新建工程时把 `_template` 复制一份改名，再写代码。如果工程要提交到 Git：

- **`.vscode/` 建议提交**：同学/同事拉下来就有同样的编译和调试配置（注意别把只属于你机器的绝对路径写进配置文件，比如 `miDebuggerPath` 就是一台机器的路径，协作者需要各改各的）。

```text

*.obj
```

### 7.8 为什么不建议新手先装 Code Runner

Code Runner 能一键运行，看着很香，但它：

- 把编译命令藏得更深，你更不知道自己执行了什么；
- 默认把输出塞进"输出"面板而不是终端，**`scanf` 经常读不到输入**；
- 报错信息不经过 `problemMatcher`，**不能点击跳转到出错行**；
- 和 `tasks.json` 的方案并存时，两个"运行"方式行为不一致，很难排查。

**先把 Ctrl + Shift + B 和 F5 用熟**，等你完全明白每一步在干嘛，再装它图省事也不迟。

## 8. 中文乱码与文件编码

这是新手问得最多的问题，值得单独一章。

### 8.1 为什么"你好"会变成"浣犲ソ"

计算机里每个字符都存成**字节**。同一串字节，用不同的编码规则去解释，得到的就是不同的文字。

```text
你写进文件的内容（UTF-8 编码，"你好"）
    E4 BD A0  E5 A5 BD      ← 共 6 个字节
                    ↓ 控制台却按 GBK（每 2 字节认一个字）来解释
    浣犲ソ                    ← 于是变成 3 个看不懂的汉字
```

所以乱码的本质**不是你的代码错了，而是"写出去的字节"和"读进来时用的规则"不一致**。

Windows 中文版的传统控制台默认代码页是 **936（GBK）**；而 VS Code 和现代编辑器默认把文件存成 **UTF-8**。两者一冲突，中文就花了。

**这意味着有三种修法，思路都是"让两边一致"：**

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 一（推荐） | 编译时指定 `-finput-charset=UTF-8 -fexec-charset=GBK` | 稳定、双击运行 exe 也不乱码 | 需要改 `tasks.json` |
| 二 | 程序里 `system("chcp 65001")` 把控制台切到 UTF-8 | 只改代码 | 只对当前终端生效；某些老环境反而出别的问题 |
| 三 | 把源文件保存成 GBK | —— | **不推荐**，会让文件在 Git、Linux、其他编辑器里出问题 |

不管选哪种，**源文件本身必须是 UTF-8**（方案三除外），这一条是底线。

### 8.2 方案一：编译时指定字符集（最稳）

在 `tasks.json` 的 `args` 里，`-g` 后面加上两行：

```json
"args": [
  "-fdiagnostics-color=always",
  "-std=c17",
  "-Wall",
  "-Wextra",
  "-g",
  "-finput-charset=UTF-8",
  "-fexec-charset=GBK",
  "-o",
  "${fileDirname}\\${fileBasenameNoExtension}.exe",
  "${file}"
]
```

含义：

- `-finput-charset=UTF-8`：**读**源文件时按 UTF-8 解释（因为你的文件确实是 UTF-8 保存的）。
- `-fexec-charset=GBK`：把字面量写进 exe 时，转成 **GBK** 字节（因为控制台默认按 GBK 读）。

于是"写出去的"和"读进来的"对上了，中文正常。

> 如果你把控制台切成了 UTF-8（方案二），那么这里应该改成 `-fexec-charset=UTF-8`。**两边必须成对**，不要一边 GBK 一边 65001。

### 8.3 方案二：把控制台切到 UTF-8

在程序开头加一行：

```c
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    system("chcp 65001 > nul");   /* 把当前控制台切到 UTF-8 */
    printf("你好，世界！\n");
    return 0;
}
```

或者只在你自己的终端里手动执行一次：

```powershell
chcp 65001
```

- `chcp` 是"change code page"的意思，`65001` 就是 UTF-8，`> nul` 表示不显示它自己那行提示。
- 缺点：它只影响**当前这个终端会话**。下次从别的地方启动程序，又要重来。
- 有些老字体在 65001 下显示方框，那是字体没有该字形，不是编码问题。

### 8.4 方案三：把源文件保存成 UTF-8（必须做）

无论选哪个方案，先在 VS Code 里确认文件的编码：

1. 看窗口**右下角状态栏**，会显示当前编码，可能是 `UTF-8`、`GBK`、`Windows-1252` 等。
2. 点它，会弹出两个关键选项，**它们完全不同，选错会毁文件**：

| 选项 | 含义 | 什么时候用 |
| --- | --- | --- |
| **通过编码重新打开**（Reopen with Encoding） | 只是"换个规则重新读一遍"，**不改文件内容** | 文件本来是 GBK 的好文件，现在显示成乱码时，选 GBK 重新打开 |
| **通过编码保存**（Save with Encoding） | 把当前内容**真正转成**另一种编码写回磁盘 | 确认屏幕上的文字是对的、要把它存成 UTF-8 时用 |

**正确顺序永远是：先"重新打开"到能看懂，再"保存"为目标编码。** 反了就会把正确的文件写坏。

### 8.5 从 Dev-C++ 迁移老文件

Dev-C++ 默认把源文件存成 **GBK**。把一个老 `.c` 直接拖进 VS Code，中文注释可能全是乱码（"浣犲ソ"那种）。正确流程：

1. 在 VS Code 里打开这个文件，**先别编辑、别保存**。
2. 看右下角编码，如果是 `UTF-8` 但文字是乱的 → 点它 → **"通过编码重新打开"** → 选 **`GBK`**。
3. 确认中文注释显示正常了。
4. 再点右下角 → **"通过编码保存"** → 选 **`UTF-8`**。
5. 保存后，文件内容从 GBK 变成了 UTF-8，中文依然正常。

### 8.6 把"新文件默认 UTF-8"固化下来

在 VS Code 里按 **Ctrl + ,** 打开设置，搜索下面两项，按建议值设置：

| 设置项 | 建议值 | 作用 |
| --- | --- | --- |
| `files.encoding` | `utf8` | 新文件默认用 UTF-8 保存 |
| `files.autoGuessEncoding` | `true` | 打开文件时自动猜编码，能减少"打开就是乱码"的情况 |

也可以直接在工程里放 `.vscode/settings.json`：

```json
{
  "files.encoding": "utf8",
  "files.autoGuessEncoding": true
}
```

### 8.7 还有几个和编码有关的小坑

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| 双击 exe 运行中文正常，在 VS Code 终端里乱码 | 两边代码页不同 | 统一用方案一；或先在终端 `chcp 936` / `chcp 65001` 试出哪个对 |
| 文件开头多了 `锘` 这种怪字符 | 文件带了 UTF-8 BOM，被当内容读了 | 用 VS Code 右下角改为"通过编码保存 → UTF-8"（不带 BOM 的那项） |
| 输出的中文变成 `\u4f60` | 不是乱码，是某些环境把非 ASCII 转义了 | 一般出现在日志/网页里，不影响程序逻辑 |
| `printf` 里有中文，编译报错 `converting to execution character set` | 目标字符集无法表示某个字符（比如 GBK 装不下的 emoji） | 换成 UTF-8 执行字符集，或别在字符串里放特殊符号 |

## 9. 多文件工程与 Makefile

### 9.1 什么时候需要多个文件

一个文件写几十行还行，写到几百行就变成一锅粥。真实工程会这样分：

| 文件 | 放什么 |
| --- | --- |
| `main.c` | 只有 `main` 函数，负责把流程串起来 |
| `math_utils.h` | **声明**："我有 `int add(int, int);` 这个函数" |
| `math_utils.c` | **实现**：`int add(int a, int b) { return a + b; }` |
| 其他 `.c` | 各自的实现 |

**头文件只写"长什么样"，`.c` 写"怎么做"。** 谁要用这个函数，就 `#include` 对应的头文件；真正把两边接起来的是**链接器**。

### 9.2 一个能跑的最小多文件工程

`math_utils.h`：

```c
#ifndef MATH_UTILS_H      /* 防止被重复包含（"头文件卫士"） */
#define MATH_UTILS_H

int add(int a, int b);    /* 只是声明，末尾有分号 */
int sub(int a, int b);

#endif
```

`math_utils.c`：

```c
#include "math_utils.h"

int add(int a, int b) { return a + b; }
int sub(int a, int b) { return a - b; }
```

`main.c`：

```c
#include <stdio.h>
#include "math_utils.h"

int main(void) {
    printf("1 + 2 = %d\n", add(1, 2));
    printf("5 - 3 = %d\n", sub(5, 3));
    return 0;
}
```

### 9.3 为什么只编译 `main.c` 会报错

如果你还是按第 1 章的 `tasks.json`（只编译"当前打开的文件"），在 `main.c` 上按 Ctrl + Shift + B，会看到：

```text
undefined reference to `add'
undefined reference to `sub'
```

翻译成人话：**"main.c 里说要调用 add，我编译完了，但整个工程里找不到 add 的实现。"** 因为 gcc 根本不知道 `math_utils.c` 的存在——你没告诉它。

解决思路只有一个：**把实现所在的 `.c` 也交给编译器。** 有两种做法。

### 9.4 方式一：把源文件都列出来（适合临时用）

```powershell
gcc -std=c17 -Wall -Wextra -g -o app.exe main.c math_utils.c
```

或者用通配符让 MinGW 帮你展开：

```powershell
gcc -std=c17 -Wall -Wextra -g -o app.exe *.c
```

在 `tasks.json` 里就是把 `"${file}"` 换成：

```json
"${fileDirname}\\*.c"
```

**它的缺点很明显：**

- 每次都全量重编，文件一多就慢；
- 通配符会把目录里**所有** `.c` 都编进去——包括你练习用的、别的带 `main` 的文件，于是报 `multiple definition of 'main'`；
- 编译顺序不受你控制。

**只适合临时验证，正式工程用下一种。**

### 9.5 方式二：写一个 Makefile（推荐）

在工程根目录新建一个**名字就叫 `Makefile`** 的文件（没有扩展名，前面也没有点）：

```make
CC      = gcc
CFLAGS  = -std=c17 -Wall -Wextra -g
TARGET  = app.exe
SRCS    = $(wildcard *.c)
OBJS    = $(SRCS:.c=.o)

$(TARGET): $(OBJS)
	$(CC) $(CFLAGS) -o $@ $(OBJS)

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

clean:
	del /Q *.o $(TARGET) 2>nul
```

> **这段代码里，`$(CC)` 那三行开头的缩进必须是 Tab（制表符），不能用空格。** 这是 Makefile 的硬性语法要求，用空格会报 `missing separator`。在 VS Code 里粘贴后，如果 Tab 被自动转成了空格，请看下面 9.6 的检查方法。

逐行解释：

| 行 | 含义 |
| --- | --- |
| `CC = gcc` | 定义一个变量 `CC`，值是 `gcc`。下面用 `$(CC)` 引用它 |
| `CFLAGS = ...` | 编译参数的变量，改一处就全生效 |
| `TARGET = app.exe` | 最终要生成的文件名 |
| `SRCS = $(wildcard *.c)` | `wildcard` 是 Make 的函数：把当前目录所有 `.c` 文件名展开 |
| `OBJS = $(SRCS:.c=.o)` | 把 `SRCS` 里每个 `.c` 换成 `.o`，得到目标文件列表 |
| `$(TARGET): $(OBJS)` | **规则**：`app.exe` 依赖所有 `.o` 文件 |
| `\t$(CC) ... -o $@ $(OBJS)` | 规则的动作。`$@` = 目标名（`app.exe`） |
| `%.o: %.c` | **模式规则**：任意 `x.o` 依赖 `x.c` |
| `\t$(CC) ... -c $< -o $@` | `-c` 只编译不链接；`$<` = 第一个依赖（`x.c`） |
| `clean:` | 一个"伪目标"，用来清理产物；`del /Q` 是 Windows 删除命令，`2>nul` 表示忽略"文件不存在"的报错 |

在终端里执行：

```powershell
mingw32-make
```

**你应该看到：** 它先编译每个 `.c` 成 `.o`，再链接成 `app.exe`。

```powershell
mingw32-make clean
```

清除所有 `.o` 和 `app.exe`。

**Make 最大的价值是"增量编译"：** 它比较每个 `.c` 和对应 `.o` 的修改时间，只重编**改过的**那些。三个文件里改一个，只编一个，这就是"构建系统"存在的意义。

### 9.6 那个 Tab 到底有没有问题

Makefile 报这个错，一定是缩进用了空格：

```text
Makefile:7: *** missing separator.  Stop.
```

检查方法：在 VS Code 里打开 `Makefile`，选中 `$(CC)` 那行开头的空白区域，看右下角/状态栏有没有显示"制表符"；或者打开"查看 → 渲染空白字符"，Tab 会显示成一个箭头 `→`，空格显示成小点。

在 VS Code 的 `.vscode/settings.json` 里加一条也能减少这种坑（对 Makefile 强制用制表符）：

```json
{
  "[makefile]": {
    "editor.insertSpaces": false,
    "editor.detectIndentation": false
  }
}
```

### 9.7 把 Makefile 接进 VS Code

把 `.vscode/tasks.json` 改成：

```json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "build",
      "type": "shell",
      "command": "mingw32-make",
      "args": [],
      "options": { "cwd": "${workspaceFolder}" },
      "problemMatcher": ["$gcc"],
      "group": { "kind": "build", "isDefault": true },
      "detail": "用 Makefile 构建整个工程"
    },
    {
      "label": "clean",
      "type": "shell",
      "command": "mingw32-make",
      "args": ["clean"],
      "options": { "cwd": "${workspaceFolder}" },
      "problemMatcher": []
    }
  ]
}
```

按 **Ctrl + Shift + B** 就是构建整个工程；要清理就跑 `clean` 任务（Ctrl + Shift + P → 输入 `Run Task` → 选 `clean`）。

注意 `cwd` 改成了 `${workspaceFolder}`：make 必须在 Makefile 所在目录执行。

> 在 MSYS2 环境里，命令名是 `make` 而不是 `mingw32-make`，两者是同一个程序。

### 9.8 一个必须改掉的坏习惯

**不要为了省事在 `main.c` 里写 `#include "math_utils.c"`。**

那样确实"能跑"，因为等于把两个文件拼成了一个文件。但代价是：

- 你绕过了链接器，等于没学会编译和链接的分工；
- 一旦两个文件里出现同名函数/变量，就是 `multiple definition`；
- 工程一大，同一个文件被多个地方包含，编译单元彻底混乱。

**正确做法永远是：头文件声明、源文件实现、编译器负责翻译、链接器负责拼接。**

## 10. 调试器：断点、单步和调用栈

### 10.1 调试到底在干嘛

调试器让你**控制程序的执行**：

| 概念 | 意思 |
| --- | --- |
| **断点（Breakpoint）** | 在某一行的**左边**点一下，出现红点。程序跑到这一行**先停下** |
| **单步（Step）** | 一次只走一行，你能看清每一步发生了什么 |
| **变量（Variables）** | 停下时，所有当前可见变量的值 |
| **调用栈（Call Stack）** | "我是怎么走到这一行的"：`main` 调用了 `f`，`f` 调用了 `g`……反过来列出来 |
| **监视（Watch）** | 你手动指定要盯住的表达式，比如 `sum`、`i * 2` |

**这就是断点调试：让程序在指定位置暂停，把那一刻的内部状态摊开给你看。**

### 10.2 一个可以照做的练习

新建 `debug.c`，**故意写一段有 bug 的代码**：

```c
#include <stdio.h>

int main(void) {
    int sum = 0;
    for (int i = 1; i <= 5; i++) {
        sum += i;
    }
    printf("sum = %d\n", sum);
    return 0;
}
```

（这段其实是对的，我们用它练手；把 `i <= 5` 改成 `i < 5` 就"错"了，正适合对比。）

操作步骤：

1. 在 `sum += i;` 这一行的**行号左边**点一下，出现实心红点（断点）。
2. 按 **F5** 启动调试（它会先自动编译）。
3. 程序停在这一行时，看左侧"变量"面板：应该有 `sum` 和 `i`。
4. 在"监视"面板（或调试侧栏的 `+`）里输入 `i`，回车；再输入 `sum`。
5. 反复按 **F10**（单步跳过），一边按一边看值：

| 第几次 F10 | `i` | `sum` 变成 | 说明 |
| --- | --- | --- | --- |
| 停住时 | 1 | 0 | 还没执行 `sum += i` |
| 第 1 次 | 2 | 1 | 0 + 1，然后 i 自增到 2 |
| 第 2 次 | 3 | 3 | 1 + 2 |
| 第 3 次 | 4 | 6 | 3 + 3 |
| 第 4 次 | 5 | 10 | 6 + 4 |
| 第 5 次 | 6 | 15 | 10 + 5，条件 `6 <= 5` 不成立，循环结束 |

6. 再按一次 **F10**，会跳到 `printf` 那一行；继续按，程序结束，终端打印 `sum = 15`。

**这个练习做一遍，你对循环、变量的理解会立刻具体起来。** 以后遇到"结果不对"，第一反应就不再是"再加几个 printf"，而是"在哪一行停下来看看"。

### 10.3 调试界面每个区域

```text
┌────────────────────────────────────────────────────────┐
│ 顶部：继续(F5) / 单步跳过(F10) / 单步进入(F11) / 重启 / 停止(Shift+F5) │
├──────────────┬─────────────────────────────────────────┤
│ 变量         │                                         │
│  i    = 3    │           编辑器（当前行高亮）           │
│  sum  = 3    │                                         │
│              │                                         │
│ 监视         │                                         │
│  sum         │                                         │
│              │                                         │
│ 调用堆栈     │                                         │
│  main  (debug.c:5)  ← 你在哪、谁调用了你              │
└──────────────┴─────────────────────────────────────────┘
底部：调试控制台（可以在这里输入 gdb 命令，新手可以先不用）
```

**单步跳过（F10）和单步进入（F11）的区别：**

- 光标停在一行**函数调用**上时：
  - **F10** 把整个函数当成一步执行完（不进去）；
  - **F11** 会**跳进**那个函数内部，一行行看它怎么跑。
- **Shift + F11**（单步跳出）：从当前函数里退出来，回到调用它的地方。

### 10.4 程序崩溃了怎么办（段错误）

先造一个崩溃：

```c
#include <stdio.h>

int main(void) {
    int *p = NULL;
    *p = 42;              /* 往空指针写数据 → 崩溃 */
    printf("never printed\n");
    return 0;
}
```

按 F5 运行，程序会异常结束，并在终端打出类似：

```text
Program received signal SIGSEGV, Segmentation fault.
0x00007ff... in main () at crash.c:5
5           *p = 42;
```

**怎么读：** 关键信息是 **`segmentation fault` + 文件 + 行号**。调用栈里**最上面那一层**通常就是炸的地方。

常见崩溃原因：

| 现象 | 常见原因 |
| --- | --- |
| 突然结束、没有任何输出 | 段错误：空指针、野指针、数组越界写 |
| 值莫名其妙地变 | 数组越界写坏了旁边的变量（栈被踩） |
| 循环跑不完 / 死机 | 循环条件写错、忘了自增、指针没推进 |
| 函数返回后崩溃 | 返回了局部变量的地址 |

调试技巧：**在可疑的地方下断点，一步步走，看哪一个变量先变得"不可能"。** 数组记得看下标是不是超了。

### 10.5 几个进阶一点点但很好用的功能

- **条件断点**：在断点上**右键 → 编辑断点 → 表达式**，填 `i == 500`。这样循环第 500 次才停下，不用按五百次 F10。
- **监视表达式**：除了看变量，还能看 `*p`、`arr[i]`、`sum / i` 这类计算结果。
- **调试控制台**：停下时可以在里面直接输入 `p x`（打印变量 x）之类的 gdb 命令；也可以临时改变量值（比如 `set var i = 10`）做实验。
- **调试前先编译**：F5 会通过 `preLaunchTask` 自动编译，所以不用担心忘了编译。

### 10.6 什么时候用 printf，什么时候用调试器

| 场景 | 更合适的方式 |
| --- | --- |
| 想快速确认"这行到底执行了没" | `printf`（打完就删） |
| 想知道循环里每一步的值 | 调试器 + 监视 |
| 程序崩溃、定位不了位置 | 调试器（调用栈直接告诉你行号） |
| 逻辑复杂、涉及指针和数组 | 调试器（能看内存里真实的值） |
| 只在特定输入下出错 | 条件断点 / 调试器 |

结论：**初学阶段把调试器练熟**，`printf` 留着做临时验证。

### 10.7 一个经典陷阱：优化 (`-O2`) 会让变量"消失"

如果你在 `tasks.json` 里用了 `-O2` 还去调试，可能会遇到：

- 变量面板显示"变量已被优化掉"；
- 单步时行号乱跳；
- 明明赋值了，值却看不到。

原因在[6.4](#64--g-和--o2-的恩怨)解释过：优化会重排代码、把变量放进寄存器、删掉"无用"的中间结果。**调试就用 `-g -O0`。**

## 11. 报错排查手册：按现象找答案

**先记住通用心法：先命令行、后 VS Code。** 出问题时，先在终端里手敲那行 `gcc` 命令：

- 命令行也失败 → 是**环境**问题（PATH、安装、文件位置）；
- 命令行成功、VS Code 失败 → 是 **`.vscode` 配置**问题。

这一招能省掉大量瞎猜。

<details>
<summary>报错：<code>gcc : 无法将“gcc”项识别为 cmdlet…</code>（或 cmd 里的"不是内部或外部命令"）</summary>

**原因**：PATH 里没有 `C:\mingw64\bin`，或者加了但终端没重开。

**怎么办**：

1. 关掉所有终端和 VS Code，重新打开一个终端再试。
2. 还不行就检查 PATH：`C:\mingw64\bin` 是否在"用户变量"的 Path 里、是否写成了 `C:\mingw64\bin\gcc.exe`。
3. 确认 `C:\mingw64\bin\gcc.exe` 文件真实存在。

详见[第 5 章](#5-path-环境变量windows-的通讯录)。

</details>

<details>
<summary>报错：<code>where.exe gcc</code> 指到了别的目录</summary>

**原因**：电脑里有第二套 GCC（旧 CodeBlocks、旧 Dev-C++、MSYS2 等），而且它在 PATH 里更靠前。

**怎么办**：把旧的那一行从 PATH 里删掉，或把 `C:\mingw64\bin` 上移到最前，**然后重开终端**。详见 [5.5](#55-why-multiple-gcc)。

</details>

<details>
<summary>现象：编译成功，但双击 exe 时窗口一闪而过</summary>

**原因**：程序确实运行了，但打印完就立刻结束，窗口随即关闭。这不是错误。

**怎么办**：在 VS Code 里按 **Ctrl + `** 打开终端，输入 `.\hello.exe` 运行；或者按 F5 调试。想让它等你按键，可以在 `return 0;` 前加 `getchar();`。

</details>

<details>
<summary>现象：中文输出变成 <code>ä½ å¥½</code> 或 <code>浣犲ソ</code></summary>

**原因**：源文件是 UTF-8，控制台按 GBK 解码。

**怎么办**：见[第 8 章](#8-中文乱码与文件编码)。最稳的是在 `tasks.json` 里加 `-finput-charset=UTF-8 -fexec-charset=GBK`。

</details>

<details>
<summary>现象：连中文注释都是乱码</summary>

**原因**：文件本身是 GBK（比如从 Dev-C++ 拖过来的），VS Code 按 UTF-8 打开了它。

**怎么办**：右下角编码 → **"通过编码重新打开"** → 选 `GBK`；确认正常后，再 **"通过编码保存"** → `UTF-8`。**顺序不能反。** 见 [8.5](#85-从-dev-c-迁移老文件)。

</details>

<details>
<summary>现象：解压出来的文件名是乱码</summary>

**原因**：压缩包创建时用的是 GBK 文件名，解压软件却按 UTF-8 去读。

**怎么办**：改用 Bandizip 解压（[3.6](#36-装一个顺手的解压软件bandizip)），并在 **选项 → 设置 → 解压 → 代码页** 里把"自动"改成 **"简体中文 (GBK, 936)"**。Windows 自带的解压没有这个设置，遇到乱码基本只能认。

</details>

<details>
<summary>现象：压缩包双击后要密码，或者只解出一部分文件</summary>

**原因**：加密压缩包需要密码；分卷压缩包被拆成了好几个文件。

**怎么办**：

- **加密包**：找发文件的人要密码，然后右键 → "解压到…"，它会提示你输入。
- **分卷包**（名字像 `xxx.zip.001`、`xxx.part1.rar`）：把**所有**分卷文件放在同一个文件夹里，在第一个（`.001` 或 `part1`）上右键解压，Bandizip 会自动把后面的接上。缺任何一个分卷都解不出来，报错里一般会写明缺哪个。

</details>

<details>
<summary>现象：代码有红波浪线，但明明能编译</summary>

**原因**：这是 IntelliSense（编辑器）的判断，不是编译器报错。

**怎么办**：检查 `c_cpp_properties.json` 里的 `compilerPath` 和 `intelliSenseMode`；保存后执行 `C/C++: Reset IntelliSense Database`。见 [7.5](#75-c_cpp_propertiesjson编辑器怎么提示)。

</details>

<details>
<summary>报错：<code>undefined reference to 'xxx'</code></summary>

**原因**：链接期找不到函数/变量的实现。

**怎么办**：

1. 函数只写了声明（在 `.h` 里），忘了在某个 `.c` 里实现；
2. 实现所在的 `.c` 没有参与编译 → 把它加进 `tasks.json` 的参数，或改用 Makefile；
3. 拼写不一致、或者 `static` 把函数限制在了别的文件里；
4. 用了数学库等第三方库却没加 `-lm` 之类的链接参数。

见[第 9 章](#9-多文件工程与-makefile)。

</details>

<details>
<summary>报错：<code>multiple definition of 'main'</code></summary>

**原因**：一次性编译了多个带 `main` 的 `.c` 文件。多半是用了 `*.c` 通配符，把练习文件也编进去了。

**怎么办**：明确列出需要编译的源文件，或改用 Makefile 并只保留一个 `main`。

</details>

<details>
<summary>报错：<code>ld.exe: cannot open output file ...: Permission denied</code></summary>

**原因**：上一次生成的 exe 还在运行（或调试会话没结束），文件被锁住。

**怎么办**：关掉正在运行的程序窗口，按 Shift + F5 停止调试，或者重启 VS Code，再编译。杀毒软件锁文件也可能导致，把它加入白名单。

</details>

<details>
<summary>报错：<code>preLaunchTask "build" terminated with exit code 1</code></summary>

**原因**：按 F5 时先执行编译任务，而编译失败了。

**怎么办**：**先去"问题"面板（Ctrl + Shift + M）看 gcc 的具体报错**，把编译错误修掉，F5 自然就好了。这个提示本身不是 bug，是"你没编过"。

</details>

<details>
<summary>报错：<code>Unable to start debugging. miDebuggerPath is invalid</code></summary>

**原因**：`launch.json` 里的 `miDebuggerPath` 指向了不存在的 gdb。

**怎么办**：确认 `C:\mingw64\bin\gdb.exe` 真实存在，然后把这个字段改成你机器上的真实路径（用正斜杠 `/`）。MSYS2 用户应填 `C:/msys64/ucrt64/bin/gdb.exe`。

</details>

<details>
<summary>现象：调试时变量显示"已被优化掉" / 值乱跳</summary>

**原因**：开了 `-O2` 之类的优化。

**怎么办**：编译参数改回 `-g -O0` 再调试。见 [6.4](#64--g-和--o2-的恩怨)。

</details>

<details>
<summary>现象：<code>scanf</code> 运行时卡住、读不到输入</summary>

**原因**：调试时程序的输入输出没接到终端。

**怎么办**：`launch.json` 里设 `"console": "integratedTerminal"`；旧版 cpptools 可改成 `"externalConsole": true`（会单独弹一个黑窗口）。

</details>

<details>
<summary>现象：杀毒软件报毒 / 编译到一半文件消失</summary>

**原因**：`gcc.exe`、`gdb.exe` 被误报。

**怎么办**：把 `C:\mingw64` 整个文件夹加入杀软白名单（Windows 安全中心 → 病毒和威胁防护 → 管理设置 → 排除项）。见 [3.9](#39-权限弹窗和杀毒软件)。

</details>

<details>
<summary>现象：Makefile 报 <code>missing separator. Stop.</code></summary>

**原因**：规则的动作行用了空格缩进。

**怎么办**：把 `$(CC)` 那几行开头的缩进改成**真正的 Tab**。见 [9.6](#96-那个-tab-到底有没有问题)。

</details>

<details>
<summary>现象：在 Git 里换行符满屏红（整个文件都显示被修改）</summary>

**原因**：Windows 用 CRLF 换行，仓库里用 LF。

**怎么办**：在仓库根目录建 `.gitattributes`：

```text
* text=auto
*.c text eol=lf
*.h text eol=lf
```

或者设置 `git config --global core.autocrlf input`（提交时转成 LF）。

</details>

<details>
<summary>现象：VS Code 里按 Ctrl + Shift + B 没反应 / 说"未找到生成任务"</summary>

**原因**：没有"打开文件夹"，或者 `tasks.json` 的 JSON 语法错了，或者任务没有 `isDefault: true`。

**怎么办**：确认左侧显示的是工程文件夹名；打开 `tasks.json` 看右下角有没有红色错误提示（JSON 语法错误会标出来）；确认 `"group"` 里有 `"isDefault": true`。

</details>

<details>
<summary>现象：JSON 文件报错，提示"意外的字符"、"属性名必须用双引号"</summary>

**原因**：多半是从网页复制时带进了中文弯引号 `“ ”`，或者多/少了一个逗号。

**怎么办**：把引号全部改成英文直引号 `"`；检查每个 `}`、`]` 后面该不该有逗号（**最后一个元素后面不能有逗号**）。VS Code 会把出错的行标红，从第一处报错改起。

</details>

<details>
<summary>现象：程序结果不对，但没有任何报错</summary>

**原因**：逻辑错误。编译器不负责发现它。

**怎么办**：**别再加 printf 猜了**，用断点调试：在循环和可疑赋值处下断点，单步观察变量。见[第 10 章](#10-调试器断点单步和调用栈)。

</details>

<details>
<summary>现象：改了代码，按 F5 还是旧结果</summary>

**原因**：`launch.json` 里漏了 `"preLaunchTask": "build"`，调试的是旧 exe。

**怎么办**：补上这个字段（名字必须和 `tasks.json` 里的 `label` 一致）。

</details>

<details>
<summary>现象：完全看不懂报错，也不知道怎么搜</summary>

**原因**：报错通常很长，新手容易只盯第一行或最后一行。

**怎么办**：用下面"怎么提问"里的三步法。

</details>

### 11.1 怎么提问、怎么搜报错

**第一步：把报错读成"位置 + 原因"两部分。**

```text
hello.c:5:12: error: 'printf' undeclared (first use in this function)
└──┬──┘ └┬┘   └─┬─┘  └──────────────────┬──────────────────┘
  文件   行列   严重程度            真正的原因（搜这句）
```

**第二步：搜索时用"原因"那一句，不要抄整个终端。**

- ✅ 搜 `'printf' undeclared` 或 `printf undeclared first use in this function`
- ❌ 搜 `我的程序报错了怎么办 C:\Users\小明\Desktop\a.c gcc …`

把路径、用户名、无关的输出删掉，问题描述会准得多。

**第三步：提问时给全下面五样东西**（少一样，别人就要多问一轮）：

1. 你执行了什么命令（原样复制）；
2. 完整的报错输出（可以贴代码块，别只截图一半）；
3. 你的系统（Windows 11 / 10）；
4. 相关文件的内容（比如 `tasks.json`）；
5. 你已经试过什么、结果如何。

**最后一条经验：一次只改一个地方。** 同时改 PATH、改 json、换编译器，出问题时你根本不知道是哪一步搞坏的。

## 12. 名词小词典

| 词 | 一句话解释 |
| --- | --- |
| **源代码** | 你写的 `.c` 文件，是给人看的文本 |
| **头文件（.h）** | 放函数/类型声明的文件，被 `#include` 进源文件 |
| **编译器** | 把源代码翻译成机器码的程序（本文用的是 `gcc`） |
| **汇编器 / 链接器** | 编译器内部的下一环：`as` 生成机器码，`ld` 把多个目标文件和库拼成 exe |
| **目标文件（.o/.obj）** | 编译完但还没链接的中间产物 |
| **库** | 别人写好的、可以链接进来用的代码集合（如标准库、数学库） |
| **调试器（gdb）** | 让程序停下、单步执行、查看变量的程序 |
| **构建系统（make）** | 根据文件依赖关系决定"先编谁、后编谁、哪些不用重编" |
| **IDE** | 把编辑器、编译器、调试器打包在一起的集成环境（Dev-C++、Visual Studio 是 IDE，VS Code 更接近"可扩展的编辑器"） |
| **终端 / 命令行** | 用打字来指挥电脑的窗口（PowerShell、cmd） |
| **环境变量** | 系统给每个程序准备的"全局设置小纸条" |
| **PATH** | 环境变量之一：列出"去哪找命令"的目录清单 |
| **工作区（workspace）** | 在 VS Code 里就是"你打开的那个文件夹" |
| **扩展** | 给 VS Code 加功能的插件（我们装了 C/C++） |
| **IntelliSense** | VS Code 的代码提示/补全/跳转/报错功能，由扩展提供 |
| **断点** | 让程序在指定行暂停的标记 |
| **单步** | 一次只执行一行地运行 |
| **调用栈** | "我是被谁调用到这里的"这条链 |
| **段错误（Segmentation fault）** | 程序访问了不该访问的内存，通常立刻崩溃 |
| **编译期错误 / 链接期错误** | 前者是"读不懂代码"，后者是"读懂了但找不到/找到多份实现" |
| **优化（-O 系列）** | 编译器为提速而重排、合并、删除代码；调试时不要开 |
| **编码 / 代码页** | 字节和字符之间的对应规则（UTF-8、GBK、代码页 65001/936） |
| **BOM** | 文件开头用来标记编码的几个字节；UTF-8 带 BOM 有时会显示成 `锘` |
| **压缩包** | 把一堆文件打包压缩成的一个文件（`.zip`、`.7z`、`.rar` 等） |
| **解压** | 把压缩包还原成原来的文件和文件夹；`.7z` / `.rar` 需要第三方软件（如 Bandizip） |
| **分卷压缩包** | 太大而被切成多个文件的压缩包（如 `xxx.part1.rar`），必须全部放在一起才能解 |
| **MinGW-w64** | 移植到 Windows 的 GCC 工具链 |
| **MSYS2** | Windows 上的类 Unix 环境 + 包管理器（`pacman`），可用来装 MinGW-w64 |
| **UCRT / MSVCRT** | C 运行库的两代实现；Win10 之后选 UCRT |
| **CRLF / LF** | Windows 与 Unix 的换行符写法不同，Git 里容易因此出现整文件差异 |

## 13. 如果学校强制你用 Dev-C++

先把事实摆清楚：**C 语言没有"Dev-C++ 版本"和"VS Code 版本"之分。编译器只认 C 标准，不认你用什么编辑器。** 你交的是 `.c` 源文件，老师拿任何编译器都能评。所谓"必须用 Dev-C++"，绝大多数时候只是老师图省事，或者他默认你不会配环境。

务实的分工：

- **交作业、上机考试**：按学校要求来，该用 Dev-C++ 就用，别跟分数过不去。
- **自己写代码、做项目、准备以后上 Linux**：用本文这套。它和课程内容完全不冲突，只会让你学得更顺。
- 如果你需要交可执行文件：Dev-C++ 默认生成 **32 位**程序，本方案默认 **64 位**。两者在现在的电脑上一般都能跑，但要拿到很老的机器上，64 位 exe 可能起不来。需要时用 `-m32` 编译（前提是装了 32 位工具链）。
- **同一份代码两边都能编译**：因为标准 C 是通用的。注意 Dev-C++ 自带的 GCC 版本很老，如果你用了新语法（比如 C11 的 `_Static_assert`、C17 的新特性），在它那里可能直接不认。**这正是"标准"重要性的最好证明。**

实在想推荐给老师，可以说：Dev-C++ 自带的 GCC 版本旧、默认 C 标准陈旧、调试器容易崩，学生用现代环境对教学只有好处。

工具是为学习服务的，不是反过来。**你花一个下午配好这套环境，换来的是往后几年写任何语言都受用的"编译器 + 编辑器 + 调试器 + 构建系统"通用认知。**

### 14.2 接下来该学什么（按顺序）

| 顺序 | 学什么 | 为什么 |

| 1 | **把调试器用熟** | 它是你未来十年排查问题的主力工具，比多学一个语法点值钱 |

### 14.3 三个小练习（检验你是不是真的会了）

1. **改坏它**：把 `hello.c` 里的分号删掉，编译一次，**读懂报错里的行号和原因**，再修回来。
2. **加个函数**：新建 `greet.c` + `greet.h`，写一个 `void greet(const char *name);`，在 `main.c` 里调用。先用"列出多个 `.c`"的方式编译，再改写成 Makefile。
3. **让它崩一次**：写 `int *p = NULL; *p = 1;`，用 F5 跑一遍，**在终端输出里找到 `Segmentation fault` 和行号**，然后用断点定位。

做完这三个练习，你已经比"只会按运行键"的人多了一整套定位问题的能力。

以后你还会遇到 `clang`、`cmake`、`ninja`、`WSL`、`Docker`，但底层那件事永远不变：**有人写代码，有人把代码翻译成机器指令，有人让程序在出错时停下来给你看。** 今天你只是第一次亲手把这几个人请到同一张桌子上而已。
