机台场地的排队，靠纸条和喊人也能维持。但人一多，问题就全冒出来了：有人不知道前面还剩几位，有人暂时离开以后没人通知，机台明明空着却迟迟没人上，管理员还得一遍遍在群里 @ 人。VirtualWait 想做的，就是把这条队伍从口头约定，变成一套能查、能提醒、能自己托管的系统。

项目地址在 [VirtualWait-Template](https://github.com/Bad0RANG3/VirtualWait-Template)。它把排队规则、身份确认、管理员操作和 QQ 群通知接在了同一条流程里，而不是散落在几个互不相干的工具中。

## 能做什么

- 按城市、区县、场地和机台四级目录展示公开队列，玩家不用进群也能看到自己排在哪。
- 玩家可以单人入队，也可以双人一起入队。
- 到达队首后需要本人确认，确认完再到场地上机。
- 游玩超时会自动回到队尾；连续两次没有确认，则自动卸卡。
- 管理员可以管理场地、机台和整条队列。
- 机台空闲时，AstrBot 插件会在 QQ 群里提醒队首玩家。

现场不用反复喊人，玩家也不用一直站在机台边上盯着。该看见的信息，会主动推到他面前。

## 设计取向

VirtualWait 把每台机台和每个玩家都当作状态机的一部分：空闲、排队中、队首待确认、上机中、超时回队尾、自动卸卡，这些状态以及它们之间的转换规则，都写在系统里。使用者只需要处理需要人判断的例外，其余交给系统跑。

自动化处理的是最耗人的那部分。队首没人应、上机超时、机台空出来，这些事本身并不复杂，却要求时刻有人盯着。VirtualWait 让超时自动回队尾，让连续两次未确认自动卸卡，再把空闲通知交给 AstrBot。**人负责运营规则，系统负责重复检查。**

身份信息单独放在 Gateway 里，和业务逻辑解耦。Gateway 默认只监听本机回环地址，Web 与 Gateway 之间用 HMAC 签名，AstrBot 插件则使用独立的 Bearer 密钥。开发环境可以用 `mock` 身份，生产环境必须换成已经授权的真实身份服务——这条边界不能省。

第一版刻意不做微服务。Next.js 加 SQLite 就能跑通整条链路，部署简单，也能离线开发。当多实例、高可用或者跨机房真的成为需求以后，再从 SQLite 迁到服务型数据库，比一开始就上分布式要划算得多。

```text
浏览器 -- HTTPS --> Web（Next.js + SQLite）
                         | HMAC
                         v
                  身份 Gateway（Python）

AstrBot 插件 -- Bearer --> Bot API --> QQ 群提醒
```

Web、身份 Gateway 和 Bot 插件彼此独立，共享同一套 JSON Schema 作为接口契约。以后想换前端、换机器人平台或者换身份服务，可以只改对应模块，不用牵一发动全身。

## 本地体验

先启动 Python Gateway，再启动 Web。开发环境可以完全离线运行，下面这条虚构身份可以直接用来走通整条流程：

```text
mock:demo-user:示例玩家:12000:示例称号
```

模板支持 `mock`、自定义 HTTP provider 以及无登录预览三种身份来源。`mock` 只适合开发与测试；上线之前，一定要接入已授权的真实身份服务，并逐项检查密钥管理、个人信息、反向代理和备份策略。

## QQ 群提醒

玩家先在自己的个人页绑定 QQ，管理员为场地配置群 UMO，再把仓库里的 AstrBot 插件装进机器人环境。插件会轮询目录摘要和热机详情，然后提醒队首玩家。启动预热、同一队首冷却以及网络退避都在插件内部处理，避免同一件事反复轰炸群聊。

## 适合谁

它适合希望快速搭起排队系统的机台场地，也可以当作一个 Next.js、Python Gateway 与 Bot 联动的单机自托管项目模板来读。

需要提醒的是，当前 SQLite 方案面向单城市、少量场地和单实例部署。要做多实例、高可用或跨机房，需要先迁移数据库，并重新验证并发与故障转移。这些不是加个副本就能解决的事。
